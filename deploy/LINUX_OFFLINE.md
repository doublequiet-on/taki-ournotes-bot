# Linux 离线发布与更新

本协议面向 Ubuntu 24.04、x86_64、CPython 3.12。仓库包含控制器源码供审核；合并应用代码不会自动替换 `/usr/local/lib/taki-updater` 中的受信控制器。服务器运行版本、控制器安装和四服采样验收须单独确认。

## 发布包

`linux-cp312.lock` 固定直接、传递依赖及构建／安装工具版本和 wheel SHA256。`pyproject.toml` 保留跨平台支持范围；生产 Linux 安装必须使用锁文件。更新依赖时有意重新解析并审查锁的差异，不能在定时更新时解析浮动版本。

Checks 的 `offline-linux-bundle` 在 Ubuntu 24.04 / Python 3.12 从完整提交导出源码归档，在临时目录解包，使用归档内的依赖锁下载 wheel 并构建应用 wheel。构建不读取工作目录内的未跟踪源码或遗留构建产物。包内只有源码归档、完整安装锁、wheelhouse 和逐文件 SHA256 清单，不包含运行配置、私有审批策略或 `local-ops`。应用 wheel 与源码都来自该提交。

`check_offline_release.py` 在 `unshare --net` 环境中创建全新 venv，执行 `pip install --no-index --find-links ... --require-hashes --no-deps`、`pip check`、安装后资源检查及源码全量回归。Windows 本地通过不能替代这个 Linux 检查。

只有 main 的 push 且两种 Python 回归和离线包验证全部成功，才发布预发行资产：

- 标签：`linux-<40位提交号>`，直接指向该提交。
- 文件：`taki-linux-x86_64-cp312.zip`。
- 重跑只接受相同标签及相同资产摘要，不覆盖已发布内容；这不是对 GitHub 仓库管理员的不可变性保证。
- PR 和其他分支只生成有保留期限的 CI artifact，不发布 Release。

服务器校验 main 的精确 Checks、标签指向、GitHub 资产摘要、包内提交号／平台／逐文件摘要。下载首次成功后缓存；首次取得的摘要也会保留，用于拒绝同一提交的资产被替换。缓存损坏会拒绝更新，不以删除锁定摘要绕过检查。最多保留三个已验证归档；回退版本和环境由原有独立保留策略保护。

## 已审核知识依赖附加包

百科语义检索使用绑定应用完整提交号的独立离线附加包，基础发布包和默认安装行为保持原协议。`deploy/linux-knowledge-cp312.lock` 固定 Linux CPython 3.12 的24项直接及传递依赖和wheel哈希。准备匹配wheel后运行：

```text
python -B scripts/build_knowledge_bundle.py --commit <应用完整SHA> --wheelhouse <已有Linux wheels目录> --output <附加包.zip>
```

工具不联网、不安装；拒绝缺失/重复wheel、浮动版本和替代下载源。包内只有精确安装锁、wheel和清单，不含百科正文、批准状态或API配置。不能在安装时重新解析传递依赖替换已审核锁。

受信配置可显式增加 `knowledge_bundle` 对象，唯一字段为 `commit`（40位应用提交号）及 `sha256`（附加包摘要）。审核后的ZIP预先存入root管理的 `<state_dir>/knowledge-bundles/<commit>.zip`。没有该配置时沿用基础安装；配置存在而提交不匹配、包缺失或改动时拒绝候选，不能静默跳过。

控制器检查根所有权、路径、外层摘要、平台、提交、成员清单、锁与每个wheel的对应关系；三个直接依赖还必须与候选pyproject的knowledge声明一致；与基础锁重叠的分发名必须具有相同版本和wheel摘要，不能覆盖基础环境的既定版本。随后在原断网、非root、限资源沙箱执行 `pip install --no-index --find-links ... --require-hashes --no-deps`，导入并核定版本，继续原安装检查、pip check、测试、兼容与素材门禁，最后才冻结环境，记录附加包身份和完整环境摘要。

ONNX Runtime初始化需要CPU信息。启用附加包的沙箱把宿主 `/proc` 替换为空的只读tmpfs，仅挂载控制器保存在root私有目录中的只读 `/proc/cpuinfo` 快照，不暴露宿主PID、environ、fd、maps或mountinfo。凭证隐藏、PrivateNetwork、User和资源限制保持原设置。未配置附加包时继续完整隐藏/proc。真实导入和进程信息不可见性需一起验收。

安装失败不生成prepared=true记录，旧版尚未停止；封存后依赖缺失或篡改仍由原environment_digest拒绝。回退读取原环境记录，不依赖当前附加包配置；不在正式venv上补装或重写摘要。本入口属于受信控制器变更，须单独审核安装；合并代码不代表线上已接入。后续提交需要对应附加包和明确配置，不自动降级到基础环境。

## 失败与重试

main／CI 元数据的 HTTP 响应读取中断（含 IncompleteRead）由适配器归类为 `github_unavailable`，下次定时检查可重新读取 CI，不把网络中断记成该提交永久失败。真正 CI 失败、提交不匹配及兼容拒绝仍阻止更新；旧失败记录不因此自动解封。该适配器属于独立控制器，合并源码仍需单独安装受审文件。

下载先使用 Release 主线路，遇到连接故障、超时或 HTTP 408/500/502/503/504 时切换同一资产的 GitHub 官方 API；不使用第三方镜像、凭据或不同版本的安装包。官方 API 请求使用 `Accept: application/octet-stream`，接受直接二进制响应和官方 CDN 跳转。CDN 签名只在内存中使用，后续分段复用，过期时重新取得，不写入日志或状态。

每轮最多三个临时故障、总下载预算 180 秒、单次连接／读取超时最多 15 秒，故障间隔 2、4 秒；HTTP 429 或明确的 API 配额耗尽交给定时器退避。收到的数据保存为提交专属 `.part`，下轮按已收到的字节继续请求，不因断线或进程中断清空。服务器忽略 Range 并返回完整文件时从头覆盖，绝不把完整文件追加到旧前缀。Range 起点、终点、总长及资产长度必须一致；最终整个包仍须通过已锁定的 SHA256 和归档清单校验，未验证的分段不能安装。普通权限错误、无效 Range、体积／摘要不符和归档结构错误直接拒绝，不用备用线路绕过。

事务会在下载开始前持久标记 `preparation_step=downloading`，在解包／离线安装前先改为 `offline_preparation`。只有仍处于下载阶段的中断能恢复为网络退避，旧进程和代码指针须仍匹配；安装／测试／兼容／备份期间的中断继续阻止目标版本。旧事务没有该标记时沿用保守恢复，不据猜测解封。

准备阶段仅 `bundle_network_unavailable`、`bundle_not_published`、`github_unavailable` 按 300、900、1800 秒退避，之后保持最多每 1800 秒一轮，由原定时器触发；这三类暂时故障不再在第三轮后永久阻止提交。v1 重试计数饱和到 3，兼容已有状态格式；成功更新后清理本提交的重试项。其他准备阶段 Deferred 仍有三轮上限，安装／测试／兼容／启动失败仍阻止提交。已存在的失败记录（包括旧控制器的 `bundle_retry_exhausted`）不会被自动删除；必要时仅对已经查明的具体提交显式 `resume --retry-commit`。版本解析或 CI 尚未完成仍按原定时器等待，不执行候选代码。

网络下载和验证均在停止旧进程之前。候选安装与测试保持无网络、无真实凭据、独立数据目录、资源限制和非 root 用户。共享数据前向／回退兼容审批、停服前备份、进程健康检查与事务回退继续生效。代码回退不还原共享游戏缓存、额度或历史数据库。

备份大小预算分别约束本次代码／环境归档和停服后的共享数据归档，每个文件最多 2 GiB；历史归档不计入本次文件预算，仍按现有保留策略管理。备份前至少保留 4 GiB 可用空间，写入期间至少保留 2 GiB，命令结束时再次核对大小和剩余空间。候选准备目录仍按整目录计算 2 GiB 预算。

## 固定谱面素材准备

依赖安装与完整离线验证通过后，`LinuxBackend.prepare` 自动执行 `scripts/prepare_note_assets.py`，在停旧实例、切换 current 之前完成固定 atlas/config 的下载和 SHA-256 校验。大 atlas 的准备下载使用固定 Git blob 的 GitHub 官方 API 原始媒体响应，避开已复现的 raw CDN 慢链路；URL 与 blob 固定在清单中，最终仍核对原来的 SHA-256，不接受可变分支、跳转或凭据。端点语义见 [GitHub Git blobs](https://docs.github.com/en/rest/git/blobs#get-a-blob)。

持久目录是启动器实际使用的 `<base>/data/game-assets`，不放进某次 release 或发行包；现存正确文件直接复用，新哈希文件原子写入，旧哈希保留，更新、回退和普通重启均可读本地素材。无需上线时人工导入。

该独立素材步骤允许匿名网络并以 ubuntu 运行，单文件下载预算 180 秒；只把候选目录和这一个游戏素材目录挂载可写，`ProtectHome=tmpfs` 继续隐藏其他共享数据，生产配置、日志、凭据仍明确不可访问。依赖安装、测试、打包及兼容验证维持断网。素材失败按既有准备失败路径拒绝候选，旧服务不停止；不清失败记录或放宽兼容门禁。步骤结束后再次检查候选源码摘要，防止准备程序改变待运行代码。

如需人工诊断仍可使用同一工具，但正常受管部署不依赖手动导入。控制器迁移仍按下文操作，禁止应用候选自行改写受信控制器；本改动的上线包括受审控制器的安装，不能只合并应用后声称已经启用。

## 只读查看进度

新版控制器安装后，在服务器终端执行：

```bash
sudo /usr/bin/python3 -E -s -B /usr/local/lib/taki-updater/linux_backend.py status --human
```

输出中文阶段、控制器记录的运行版本、观察目标、已收到／总字节和最早重试时间（UTC，实际执行由定时器触发）。命令不触发下载、状态写入、恢复或服务操作；`status` 不加 `--human` 仍输出 JSON，额外含经过筛选的下载摘要。缓存下的 `<SHA>.download.json` 只保存阶段、线路名、字节数和时间，不包含签名 URL、凭据或 QQ 数据。

这里显示控制器的状态快照，不联网判断远端最新版，也不代替实际进程路径、当前启动日志和 QQ 功能验收。旧控制器不支持这个选项；仅合并源码不能让上述命令在线上生效。

## 现有服务器的控制器迁移

新增的 `linux_backend.py`、`linux_updater.py` 是此前独立 Linux 控制器源码的受审版本；保留线上安装步骤 1800 秒、其他步骤 900 秒的运行上限。原先只针对本地私有审批快照的测试改为构造审批样例检查，私有策略没有随源码提交。

这三个文件需要一起审核、备份和替换：`linux_backend.py`、`linux_updater.py`、`offline_bundle.py`。不要从应用候选代码中自动自更新控制器，不替换 launcher、systemd 单元、生产配置、兼容策略或已审核夹具。

迁移前先核对线上文件摘要与已检查基线，确认更新器没有活动事务、旧机器人健康、备份可读。暂停更新定时器并取得现有控制器锁，在受信目录同文件系统中暂存和校验新文件，保留旧文件及回退清单，完成整组替换和导入检查后再恢复定时器。意外中断应保持定时器停止，恢复整组旧控制器后再恢复调度。不要中止正在切换版本的事务，也不要因安装控制器直接重启机器人。

先确认新 main 的精确 CI 和 Release 均完成，再让新控制器处理该提交；缺少发布包时应等待，不回退在线 pip。旧失败提交只在明确需要时单独恢复，不能批量清空失败列表。

## 新版验收与采样交接

1. 核对 `current`、运行进程使用的代码／venv、控制器状态记录三者均指向验收提交；确认新 PID 的 QQ ready、至少 20 秒稳定及无启动错误。CI 成功不代表服务器已经更新。
2. 确认 Note 来源修复、查询和资源验证通过。保留既有限制：旧版本完整刷新重写缓存后，新版必须重新获取来源，才能把零值确认成真实零；来源未恢复时显示未知，不补造零。
3. 新版验收通过后，按用户已授权范围启用四服 300 秒采样；配置合入现有环境，不覆盖密钥，不清历史数据。以实际进程环境、SQLite 四服观测及多轮时间戳作为证据，不把配置文件存在视为已启用。
4. 更新 QQ 控制台面板属于外部操作，需核对实际面板内容及回执；机器人上线不等于面板更新，也不等于消息已经送达。

离线包用法依据 [pip 可重复安装](https://pip.pypa.io/en/stable/topics/repeatable-installs/)；资产下载与摘要依据 [GitHub Release assets API](https://docs.github.com/en/rest/releases/assets)，分段语义依据 [HTTP Range 协议](https://www.rfc-editor.org/rfc/rfc9110.html#name-range)。

## 查询素材准备

同一候选准备阶段还执行 `scripts/prepare_query_assets.py`：取同版公开 Catalog，预下载角色立绘、卡面、缩略图、封面、活动/卡池及乐队图标，从同版活动／挑战索引补齐榜线小封面和章节横幅，同时校验全部固定游戏素材。只允许 release 固定的来源 URL；图片须完整解码且符合字节/像素预算。`prepared-artwork-v1.json` 保存来源身份及每张图片的 SHA-256，全部成功后原子发布；损坏或缺失文件重新获取，失败阻止候选完成准备，旧服务继续运行。

素材仍存于 `<base>/data/game-assets` 和 `<base>/data/haneoka-asset-cache`。该步骤只额外挂载这两个目录，不开放整个共享数据目录；候选 Catalog 保存在候选 `test-data` 中，不覆盖正在运行的资料快照。更新、回退和重启沿现有 URL 哈希缓存读取已准备素材。诊断可运行 `python -B scripts/prepare_query_assets.py --cache-dir <隔离数据目录> --catalog <隔离Catalog文件>`；`--snapshot` 固定使用指定已有 Catalog 快照，仍会按其 release 身份请求活动／挑战索引并下载缺失素材；它不是断网开关。榜线绘图读取同一持久图片缓存，不受独立榜线小时缓存是否为空影响。准备耗时应与首次查询、热缓存查询耗时分别记录。

受管理的 Koishi 后端由 `koishi_launcher.py --base <base> backend` 在启动时将 `OURNOTES_RUNTIME_DATA_DIR` 固定为 `<base>/data`，覆盖旧 EnvironmentFile 遗留值，保证预热和查询读取同一目录。直接运行 backend 的隔离目录配置不受影响。安装该启动器须单独核验并备份原文件；应用包更新不会自动安装控制器。上线检查应核对实际进程环境，而不只看 systemd 示例文件。旧运行目录不删除、不合并：其中可重建的成员／谱面缓存将按原刷新规则在新目录建立；必须保留管理模板中显式的 `OURNOTES_CACHE_FILE`，以及已有的额度、历史和统计路径配置，使业务数据继续从原路径读取。若省略主缓存配置，其默认路径和由它派生的业务路径也会随运行目录改变，应先核对并显式固定已有路径，再安装启动器；不自动搬迁数据。切换前检查两个目录的业务数据归属及 `<base>/data` 的写权限，按既有流程备份并先停旧实例。
