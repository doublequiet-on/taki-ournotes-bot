# L2 Deploy — 本地环境准备与启动入口

> 本页描述 `deploy/` 的当前职责、启动分流及协作边界。操作步骤由 README 和专项说明维护。

## Purpose

`deploy/` 集中提供 Windows 本地环境准备、机器人启动入口，以及部署依赖清单和简要说明。它把仓库布局、Python 环境和应用入口接起来，使调用者不必在每次启动时自行拼装路径。

当前规模使用一个 L2 即可：准备与启动是同一目录内的两个入口，没有需要独立文档维护的复杂实现子域。暂不建立 L2-2；本页链接脚本和现有说明，不要求 Markdown、依赖清单套用源码文件头 L3。

## Responsibilities / Non-Responsibilities

- 定位仓库根目录，准备或复用本地 Python 环境，保留已有配置，调用应用的数据同步入口。
- 根据更新器状态文件是否存在，选择受管启动或直接应用启动。
- 提供部署便利依赖清单及说明；项目安装依赖的权威定义仍是根目录 [pyproject.toml](../pyproject.toml)。
- 不实现数据解析、查询、QQ 收发或通知；这些能力属于 `src/`。
- 不拥有版本验证、更新事务、进程识别、计划任务注册或回退；这些由 `scripts/` 中的更新器和任务安装脚本负责。
- 不提供完整服务器编排。目录 README 中的服务器说明只是模板，不能据此认定存在自动服务器部署能力。

## Inputs / Outputs

查询升级发布配置见 [query-upgrade-v1.env.example](query-upgrade-v1.env.example)；只包含四服采样与容量参数，须合入服务器已有环境，不替换密钥或自动启用。轮询安装默认关闭，长期保留与恢复规则见 [历史运维](../docs/CUTOFF_HISTORY.md)。

输入包括仓库布局、本机 Python 启动器或既有 `.venv`、项目依赖声明、配置模板或已有环境配置，以及可选的更新器状态。

准备入口尝试产出可用虚拟环境、首次 `.env` 和同步后的资料缓存；启动入口进入直接机器人进程，或请求更新器检查／恢复／启动受管版本。启动请求不等于 QQ 已上线，更不等于消息已送达。

## Core Contracts

| 契约 | 当前约定及所有权 |
|---|---|
| 仓库位置 | 两个脚本均以 `$PSScriptRoot` 的父目录定位仓库，切换到该目录，并设置当前进程 `PYTHONPATH` 为根目录下的 `src`。因此脚本位置与仓库布局有明确耦合。 |
| 本地解释器 | 使用仓库 `.venv/Scripts/python.exe`；准备入口在其不存在时调用本机 Python 启动器创建环境。 |
| 安装声明 | 准备入口检测关键模块能否导入；失败时安装构建所需工具并以 editable 方式安装项目。它不直接读取 `deploy/requirements.txt` 安装，也不保证每次运行都升级或重新核对所有依赖。 |
| 配置 | 仅在根目录 `.env` 不存在时复制 `.env.example`；配置字段、默认值和加载优先级归 [config.py](../src/ournotes_bot/config.py) 与 [.env.example](../.env.example)，本页不复制。 |
| 启动分流 | `data/updater/state.json` 存在即委托 [update_bot.py](../scripts/update_bot.py) 的 `--start`；文件是否有效及活动版本是否可运行，由更新器判断。 |
| 应用入口 | 准备与直接启动分别进入 [main.py](../src/ournotes_bot/main.py) 的 `sync` 与 `bot` 模式；模式内部逻辑见 [Application 地图](../src/L2-Application.md)。 |
| 发行内容 | [MANIFEST.in](../MANIFEST.in) 将两个脚本和依赖清单纳入源码发行包；这不等于它们属于安装后的 Python 包 API。 |

更新器状态字段、事务恢复与写入规则由 [Scripts 地图](../scripts/L2.md)及更新器实现维护；本目录只需要知道分流入口。

## Internal Flow / Dependencies

```text
准备入口 → 本地环境检查／必要安装 → 首次配置复制 → main sync → 数据加载与缓存
启动入口 → 检查更新器状态文件是否存在
         ├─ 存在 → update_bot --start → 更新器恢复／实例检查／受管启动
         └─ 不存在 → 本地环境与凭据前置检查 → main bot → QQ 运行
```

分开准备和启动，是因为安装、配置初始化与资料同步具有独立副作用，不应成为每次直接启动脚本必做的操作。但应用启动自身仍可能加载资料、联网或写缓存，不能把“启动”描述为纯读取。

受管分支复用更新器的锁、实例检查和恢复机制，避免在部署入口再实现一套进程管理。它通常复用已保存版本；若有未完成事务，会先走恢复流程，不能描述为只读检查或无条件运行当前工作树。

依赖方向为 `deploy → scripts 更新器` 或 `deploy → src 应用入口`。应用业务模块无需反向导入这些 PowerShell 脚本。安装声明、配置模板与打包清单位于仓库根，是跨目录契约，不因被 deploy 使用就归入 deploy。

## State / Side Effects

准备入口可能创建 `.venv`、安装依赖、创建 `.env`，并联网读取资料、写缓存；已有 `.env` 保留。两个脚本均会改变所在 PowerShell 进程的当前目录和环境变量。

直接启动可能建立 QQ 连接；受管启动可能触发进程／任务操作和事务恢复，其状态写入归更新器。部署入口不负责回退共享游戏缓存、额度或通知数据库。

## Failure / Degradation Boundaries

- 直接启动分支缺少本地解释器时中止；缺少 `.env` 且未同时提供两个 QQ 环境变量时中止。`.env` 存在只是通过脚本前置检查，不代表凭据有效，后续由应用校验。
- 受管分支先于上述直接启动检查，使用根目录解释器调用更新器并显式返回其退出码。状态文件损坏或更新器拒绝启动时，不自动退回直接启动绕过保护。
- 准备入口对两次安装命令显式检查退出码；创建虚拟环境和最终同步之后没有同样的显式检查。尤其同步失败后仍可能打印准备完成提示，不能以该提示作为成功证明。此处记录当前边界，不在文档阶段修改脚本。
- 直接启动末尾没有与受管分支相同的显式退出码转发；本页不承诺两个分支具有完全一致的外层退出行为。

## Linux 离线更新控制器

本目录另提供独立安装的 Linux 控制器受审源码：`linux_updater.py` 管持久事务、重试预算和回退，`linux_backend.py` 管 systemd 隔离、兼容门禁和候选准备，`offline_bundle.py` 管发布包验证与缓存，`linux-cp312.lock` 固定生产依赖。它们不由 Windows 启动脚本调用，也不会随应用安装自动替换线上控制器。职责、失败边界和迁移见 [LINUX_OFFLINE](LINUX_OFFLINE.md)。前文 Windows 入口的非职责约束仅适用于两个 PowerShell 脚本。
