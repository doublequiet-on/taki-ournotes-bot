# 歌曲查询与谱面展示更新报告

本次以 `main@46e47feeb6c4988fc1d66b573705552e72cbbfc9` 为审查基线。角色卡／SNAP 图鉴与上传修复已在上一批发布，本次不重复实现。最终提交、CI 与合并 SHA 由关联 PR 记录；本报告随代码保存，便于按版本追查。

## 用户可见变化

- `/查曲` 新增颜色、包含某类激奏、纯类型、混合及精确顺序筛选，可与歌曲／乐队、难度、等级、分页组合。`JUST/JUST/COMBO` 保留重复与顺序，不能当作无序集合。常见 `/问` 在本地转为相同查询，不调用模型。
- 歌曲列表与谱面详情共用“歌名前属性图标、标题下紧凑激奏框、左下角 ID／乐队”布局。框宽随内容收紧，长标题和缺失提示参与高度测量；图标不可获取才回退文字，不伪造图标。分数表采用同款属性标识和激奏摘要，仍按原口径展示最多30条谱面。
- 静态谱面目标密度从每拍52提高到78逻辑像素，较长歌曲采用六栏。阅读方向、长条节点、左右位置、划键语义不变。编码缩放后增幅因曲长与图像复杂度而异，不承诺手机缩略图统一增加50%。
- 更新 `/帮助`、新增 `/介绍`，并更新 QQ 指令面板定义。平台面板需执行 `setup-menu` 才生效，QQ资料页简介仍由控制台维护；不能将代码变更当作平台已发布。

## 数据与来源

使用 Haneoka **日服**公开接口 `https://haneoka.org/api/v1/servers/jp/`，以 `release?projection=identity` 固定版本后读取 `songs`、逐条 `songs/{ID}` 与 `gekisou`。核实版本、源码及最小真实样例详见 [THIRD_PARTY.md](../THIRD_PARTY.md#歌曲颜色与激奏顺序)。本次来源快照含84首；与本地资料按 ID、已知标题、封面标识共同校验，未映射记录不强行合并，84并非生产覆盖数保证。

`musicType` 对应五种属性颜色；`gekisou.missionTypes` 对应歌曲主表的三段激奏顺序，1=COMBO、2=LUCK、3=JUST。这些字段不是卡牌技能，也不从谱面 Fever 区间推算。图标复用已核实的 Project Yume `CardType1..5.webp` 公共素材，按需缓存，不打包游戏图片。JUST／COMBO／LUCK各自的原生小图标尚未核实，本轮只展示类型文字与顺序箭头。

## 模块职责与审查

| 模块 | 职责与边界 |
|---|---|
| `song_traits.py` | 日服版本固定、字段校验、精确关联、独立缓存；不依赖QQ或模型 |
| `song_query.py` | 颜色／激奏条件解析、过滤和同份分页结果；未知条件拒绝，不扩大范围 |
| `data.py` | 将属性附加到不可变歌曲记录，主库与属性刷新短锁保护赋值，网络下载不持锁 |
| `commands.py`、`local_query.py`、`structured_query.py`、`query_capabilities.py` | 复用现有直接指令及自然语言入口；本地结构化条件共用执行器 |
| `efficiency_query.py`、`visuals.py` | 捕获同份歌曲事实；共用标题／激奏绘制组件，不在渲染时重新查询或改指标 |
| `qq.py` | 独立后台属性刷新，在线程执行；沿用顺序、文字回退与不盲重发规则 |
| `bot_info.py`、`menu.py`、`main.py` | 简介和面板定义；安装面板不初始化AI、不刷新游戏缓存 |

审查修正了自然语言路由丢失新条件、显式小数等级与整数等级含义、上游详情字段变形、并发刷新覆盖，以及长文本挤压布局的问题。分数表测试改查实际编码预算，不再要求长图缩放后保持固定宽度。新增测试集中在行为与故障边界，没有为每种样式单独复制测试脚本。

## 缓存与回退

无需新增配置。`haneoka-song-traits-jp.json` 独立存放于主缓存旁，24小时有效，失败后至少5分钟再试；启动后台获取，不在群查询中下载全站。一次刷新串行去重、详情最多4并发，缺记录／重复／HTML／新枚举等校验失败保留旧文件。`fetched_at` 明确是本机成功获取时间。

旧主缓存歌曲行不写入新增 `traits` 字段。使用本地公开预览资料生成新主缓存，再以基线版本真实读取器读取：83首歌曲、60张成员卡、62张SNAP均成功。代码回退不需要删除主缓存、属性缓存或额度；旧版本忽略独立属性文件。数据源故障不阻断原歌曲与卡牌查询。

沿用全局图像预算：JPEG≤1,500,000字节、最长边≤8192、总像素≤1200万，保留所有列表行与完整谱面。未改上传重试和群公告发送策略。
