# 更新通知机制

## 职责与边界

发布公告是跨目录运维主题中的运行时能力：读取已提交部署身份，生成面向群友的发布摘要，并持久记录群发现、许可和发送尝试。它不负责部署、回退、普通查询或 Query 的额度统计。

QQ 提供连接、群事件与后台任务生命周期；公告模块当前自己使用 `botpy.http.Route` 和 SDK HTTP 对象主动发送，不经过 QQ 的被动回复函数。它仍位于 `src/ournotes_bot/update_notice.py` 根部；通知专题不建立新的 Operations 父 L2 或 L2-2。

## 入口与依赖

| 入口 | 职责 |
|---|---|
| [update_notice.py](../src/ournotes_bot/update_notice.py) 的 `NoticeStore` | 保存群状态、报告生成占位及发送记录。 |
| `committed_notice` | 校验可公告的部署身份，返回活动和前一版本 SHA，或阻止本轮公告。 |
| `release_facts` | 用配置好的 Git 读取公开提交标题、变动文件和更新日志增量。 |
| `UpdateNotifier` | 复用或生成报告，处理许可、发送占位、主动请求和结果记录。 |
| [qq.py](../src/ournotes_bot/platforms/qq/qq.py) 的 `run_bot`／`ClientWithRefresh` | 组装 notifier，接入群事件，在 ready 时维护通知 worker。 |

部署状态的字段与写入／恢复语义由 [Scripts 的部署状态协议](../scripts/L2.md#部署状态协议)维护。本专题只解释下游读取条件。配置以 [config.py](../src/ournotes_bot/config.py) 与 [.env.example](../.env.example) 为准；报告使用共享 [AIClient](../src/ournotes_bot/ai_client.py)，独立于查询的额度与统计。

QQ 在通知开关开启时构造 `UpdateNotifier`；只有存在 AI 密钥时才给它配置 AI 客户端。无客户端会阻止生成新报告，但 `_report` 先查已保存的 ready 报告，因此仍可能复用并发送已有报告。关闭全局通知开关才会使这条组装路径不创建 worker。

QQ 的缺密钥日志写作“不会生成或发送群公告”，诊断时仍须结合上述 ready 报告复用分支判断；该日志不能证明已有公告一定不会发送。

## 触发条件与处理流程

`committed_notice` 要求无未结束切换事务、部署状态存在、活动及前一版本 SHA 符合格式、活动 source 与本进程 source 一致，以及没有问题提交标记。部署身份来自共享文件协议，不能由 HEAD、进程存在或 ready 文件单独推出。`RELEASE_SOURCE` 按当前文件物理位置计算，不能因目录整理改变它。

```text
校验部署身份 → 复用 ready 报告，或预占生成记录 → 读取发布事实并调用 AI
            → 校验文案 → 再核对部署身份 → 读取待通知群
            → 限速查询许可 → 再核对部署身份 → 限速并再次核对
            → 持久化发送占位 → 主动 POST → 保存回执或失败状态
```

`deliver` 用实例内异步锁串行处理；它没有全程持有部署锁，也不与更新器形成跨进程原子事务。报告生成等待之后、许可查询之后及发送前的限速等待之后，均重新核对部署身份；这些检查降低旧版本发送的机会，不消除检查与外部请求之间的竞争窗口。

报告生成前先占位，再由后台线程读取事实和调用模型。`release_facts` 从 `settings.json` 读取有效 Git 路径，读取前一版本到活动版本的公开提交标题、文件名及 `更新日志.md` 新增行；不发送群标识、聊天正文或密钥作为报告输入。

模型提示要求简短中文和群友可感知变化；代码要求 `notice` 为字符串，移除既定标题前缀、合并空白，拒绝超过 120 字或包含受禁技术词的文案，并拒绝与前一 ready 报告完全相同的非空文本。空字符串记为跳过。提示中的句数要求及事实准确性没有被程序完整验证，不能把通过格式检查写成模型事实已获证明。

## 通知账本与去重

账本默认位于游戏缓存旁的 `update-notices.sqlite3`。SQLite 唯一键和外部调用前的持久占位控制尝试，不代表平台 exactly-once 送达。

| 记录 | 唯一键与状态 | 职责 |
|---|---|---|
| `groups` | AppID、群；保存 `present`、`allowed`、`event_at` | 群是否仍在、已知主动许可及事件顺序。未知许可为 NULL。 |
| `release_reports` | AppID、版本；`generating` → `ready`／`failed`／`skipped` | 在付费生成前占位，同 AppID 的多个群复用 ready 文案；不同 AppID 独立。 |
| `notices` | AppID、群、版本；`sending` → `sent`／`failed`／`uncertain`，或 `disabled` | 外部发送前占位，记录结果；明确不允许时记录 disabled 并跳过 POST。 |

`reserve_report` 和 `reserve` 用唯一键插入，竞争者不会重复占位。崩溃可能留下 `generating` 或 `sending`；下次进程不会因重启自动重试该记录。`pending` 排除所有已有发送记录，包含失败、不确定和 disabled 状态，可能因此漏掉当次公告。

报告复用范围是 AppID＋版本，发送尝试范围是 AppID＋群＋版本。新版本使用新的键；新增发现且尚无该版本记录的群也可能在后续轮询中处理，不能笼统承诺“重启后绝不再广播任何群”。

## 群发现、许可与交付

普通群消息只发现群，不能授权主动发送，也不能把已退出或拒收状态改回允许。QQ 接入同时转发入群、退群、接收主动消息和拒收事件；较旧事件不覆盖较新状态。无法转换为数值的事件时间使用当前时间，负值或非有限值则忽略该事件。

发送前尽量查询群的 `bot_state`。只有返回明确布尔许可时才写入本地许可，且要求查询前后的 `event_at` 相同，避免旧查询覆盖期间收到的新事件。查询异常保留已知状态；当前代码注释将该 GET 标为白名单接口，本轮未重新验证平台规则。

退出群不会进入待发送列表；本地明确拒收时 `reserve` 留下 disabled 记录并跳过发送。许可未知时仍可尝试真正的主动 POST，由 QQ 校验权限，不能把“发现群”写成许可，也不能声称只有本地明确允许才调用 POST。

GET 与 POST 经 `_pace` 间隔控制。POST 使用主动消息路由和普通文本请求，不借旧 `msg_id`／`event_id` 伪装被动回复；当前传入 `retry_time=2`，按源码中的 SDK 兼容处理避免连接结果不确定后重复发送。只有返回非空字符串消息 ID 才记录 sent；该记录不证明群友实际阅读或完整端到端验收。

## 失败与恢复边界

| 情况 | 当前处理与限制 |
|---|---|
| 无 AI 客户端 | 无现成 ready 报告时不生成、不预占；已有 ready 报告仍可复用。 |
| 发布事实读取失败、模型请求失败、非法类型／长度／技术词或重复文案 | 已预占报告转为 failed，不自动重新生成。 |
| 模型返回空报告（用于跳过内部维护等情况） | 记录 skipped，不发送；相同 AppID／版本不反复生成。 |
| 数据库读取或写入故障 | 本轮通知停止，worker 捕获异常并继续后续轮询；可能留下占位，不自动清理或补发。群观察异常单独记录，不破坏查询路径。 |
| 明确拒收或退出 | 跳过主动请求；disabled 或其他已有发送记录不会因随后开关变化被自动重试。 |
| POST 异常 | 记录 failed；该群不自动重发，其他群通常可继续，除非账本故障使本轮中止。 |
| 无有效消息 ID | 记录 uncertain，不自动重发。 |
| 发送中断或进程退出 | 可能留下 sending；重启不重试，保守避免已送达但未拿到回执造成重复。 |

通知失败不触发代码回退，也不保证公告最终送达。现有 CLI 没有公告补发或报告重试命令；更新器的 `--retry` 只处理部署候选，不改变通知账本。不可通过删除数据库或占位来承诺安全重发。

QQ 重连时复用仍在运行的通知任务；任务已结束时可重新创建。`run` 轮询异常只记录错误类型并继续等待，不输出原始响应；群日志使用哈希标签，账本中的真实标识和回执仍应作为本机状态保留。
