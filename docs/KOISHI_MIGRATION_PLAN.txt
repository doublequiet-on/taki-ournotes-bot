1. 目标、交付范围与完成定义
============================================================

1.1 用户目标

让 Taki 使用 Koishi 的平台接入、命令入口和日常管理能力，同时继续使用现有 Python 查询、数据、自然语言解析、绘图与业务状态。

迁移完成时：
- 群友继续使用现有已开放命令、别名、参数、图片和续查方式。
- Koishi 负责当前已开放的 QQ 接入、消息归属和实际发送。
- Python 后端负责 ON 业务、绘图、资料与状态，能够不连接 QQ 独立启动。
- 资料刷新、属性刷新、活动榜单采样和已启用的通知功能有明确管理者。
- 两个运行部分有明确的版本兼容、健康检查、发布和回退机制。
- Taki 不需要全面重写为 TypeScript，也不要求把每项业务拆成 Koishi 插件。

1.2 当前迁移范围

按实际工作区和运行配置核对现有能力，覆盖当前已开放的：
- 歌曲、条件筛选、谱面及相关详情；
- 成员卡、留影卡/SNAP、人物、卡池及活动资料；
- 四服活动挑战歌曲 Top 100 观测及已实现的相关历史查询；
- 直接命令与“/问”的本地优先、受限模型解析；
- 单消息多命令、图文结果、长文字、多图及“/继续”；
- 已实现的有限选择与分页续查；
- 查询容量、AI 额度、缓存和来源失败语义；
- 当前已启用的群聊、私聊、后台任务与更新通知。

当前主分支的歌曲分数表已移除，配队和新激奏选曲对比不能列为已经存在的迁移功能。[S1]
若执行时这些功能已新增，只核对实际代码并纳入相关入口兼容；不得借本任务重新设计游戏公式。

1.3 本次不扩大的范围

- 不重写查询器、数据源适配器或整套 Pillow 绘图。
- 不另建面向公众的业务 API、共享多租户服务、插件市场、模板市场或分布式集群。
- 不迁移到 OneBot/NapCat，不更换 QQ 应用身份作为默认实施动作。
- 不新增自由聊天、攻略推荐、账号操作或付费模型功能。
- 不把业务缓存、AI 额度、榜单历史全部搬进 Koishi 数据库。
- 不以架构美化为由全仓移动文件、批量改命名或放宽架构门禁。
- 不把两个旧、新完整 Taki 运行时同时连到同一生产机器人并共同写同一数据目录。

1.4 两种完成状态必须分开

A. 开发交付完成：
代码、锁定版本、离线与模拟集成验证、发布产物方案、兼容矩阵、切换/回退操作包完整；缺少的真实验证明确列出。

在 A 的基础上，目标环境实际采用对应版本组合，QQ 已开放场景实机验收通过，后台任务与数据写入正常，更新和回退路径已验证。

2.1 核心事实

- 项目为 Python；pyproject.toml 声明 qq-botpy==1.2.1、Pillow>=11,<13、aiohttp>=3.9,<4，支持 Python>=3.10。[S2]
- main.py 已有 query、repl、sync、bot、setup-menu 模式；没有本文提出的 HTTP 后端模式。[S3]
- CommandResult 在 commands.py；QuerySpec/QueryResult 在 structured_query.py。直接命令并非全部先转 QuerySpec，不强行改为一种入口。[S4][S5]
- application/reply_preparation.py 已提取部分歌曲/谱面回复准备，可复用；目前不是通用后端服务。[S6]
- qq.py 同时承担平台事件、应用编排、准备限流、发送顺序、PreparedReply、DeliveryCursor、回执和后台任务接线。[S7]
- query/continuation.py 的 ContextStore 默认容量 1024、TTL 600 秒，并有 generation/lineage 防迟到覆盖；这是有界运行期状态。[S8]
- 现有 QueryGate 默认 2 个准备任务 + 4 个等待位置；线程任务取消后仍占容量直至实际结束。执行时以当前配置为准。[S7]
- 当前 ReplySequencer 是一个全局批次序列，跨群和 C2C 共享；不是“每群锁”，且有超时退化，不保证绝对严格顺序。[S7]
- 当前群消息去重是进程内 deque(maxlen=256)，C2C 没有同等去重；不得称现有系统已具备全链路幂等。[S7]
- DailyQuota 明确只有单进程锁，不支持多进程共同写同一额度记录。[S9]
- 刷新、属性刷新、HistorySampler 和 UpdateNotifier 当前由 QQ 生命周期组装。[S7]
- UpdateNotifier 仍直接使用 QQ API，不能当成已经平台无关。[S10]
- Linux 更新器按特定 QQ “已上线”日志和服务状态判就绪；控制器源码合并不等于已安装控制器改变。[S11][S12]
- 仓库已有核心无 QQ 依赖测试与架构门禁；不能因为新服务而放宽这些规则。[S13][S14]

3. 推荐架构与职责归属
============================================================

3.1 运行形态

同一仓库、同机两个常驻进程：
- Koishi 进程：官方 QQ 适配器 + 本地 Taki 接入插件。
- Python 进程：Taki 应用核心 + aiohttp 本机接口 + 数据任务。

后端优先复用当前 aiohttp 依赖。不要每收到一条命令就启动 Python CLI，也不要在插件加载时临时 pip/npm 安装或偷偷拉起一套 Python 服务。

第一版保持一个 Python 业务进程和有界线程任务；不启多 worker 共同写当前文件状态。正常服务启动交给现有进程管理方式。

3.2 Python 管理

- SongRepository 和当前来源/缓存配置；
- 命令正文解析、别名、消歧、条件、结果状态；
- /问 的本地解析、模型提议、校验、AI 额度和指标；
- PreparedReply 等价结果、渲染准备、Pillow 编码、完整备用文字；
- 完整已捕获结果、余图游标、选择上下文、generation/lineage；
- QueryGate、有界工作和计算等待；
- 后端请求与交付记录、回执后的业务提交；
- 资料刷新、属性刷新、HistorySampler；
- 更新报告生成和通知账本的业务部分。

内部继续复用现有 CommandResult/QueryResult/QuerySpec。不要为了跨语言接口把全部 Python 对象序列化给 Koishi，也不要让 Query/Rendering 反向导入平台 SDK。

3.3 Koishi 薄插件管理

- Taki 命令入口、别名、帮助接入与功能使用范围；
- 当前事件的原始 Session、平台与机器人身份；
- 从事件提取普通身份字段和业务正文；
- 对同一入站消息的批次在到达时登记顺序；
- 发送时限、实际发送次数预算、消息序号的统一管理；
- 按结果片段顺序上传/发送，获得真实平台回执；
- 向 Python 回报发送过程与结果；
- 平台群事件及通知发送接线；
- 插件停用时停止新请求、清理监听和等待，禁止旧实例继续发消息。

Koishi 不重新实现歌曲别名、技能筛选、数据源逻辑或 AI 事实判断。

3.4 只有一方决定发送顺序

建议将实际批次排序放在 Koishi，Python 只负责准备和业务状态：
- 为每条入站消息先取到达票号，再请求后端准备。
- 发送排序与业务接纳排序分别建模。Koishi 保留到达顺序，Python 依据已验证的接纳顺序建立 generation/捕获 lineage；不得把 HTTP 抵达顺序当成用户请求的新旧顺序。关闭发送排序不关闭此项约束。
- 第一版保留现有全局排序、配置开关和超时退化语义。
- 同一消息内命令、页与备用文字始终按原顺序交付。
- Python 不再为同一发送链路运行第二套 ReplySequencer。
- 旧 botpy 入口调用共享应用层时，可由旧入口保留自己的平台排序器。
- 所有退出路径释放排序票号；释放票号不等于提交续查。
- 若确有必要改为各会话独立排序，作为明确行为调整记录并单独验收，不夹带在迁移中。

4. Koishi / QQ 发送能力前置门禁
============================================================

4.1 锁定实际安装组合

执行方记录：
- Node 版本；
- 实际安装的 Koishi、QQ adapter 和关联 Satori 包版本；
- 唯一使用的包管理器、依赖树和 lockfile；
- 所选 QQ 连接方式、事件类型和发送接口；
- 群聊/C2C 各自验证范围与能力配置。

本文参考过 Koishi 提交 97d5c395750cec37b772e0b94dc63c427e3bb868，以及 Satori v4 提交 7606a0c3bd1ec7756a893bfce4129db9548df213。[S15][S16]
它们只证明这些源码快照的实现，不能证明某个 npm 稳定安装组合具有同样行为。不得直接使用 main、latest 或文档旧示例代替锁定和核验。

4.2 优先验证的发送路径

用实际安装版本验证保留原 Session 的高层发送是否同时满足：
- 原消息被动回复归属正确；
- 实际 QQ 调用次数可预测；
- 每个应用片段可取得可归属的真实消息 ID；
- 空回执、审核中、明确拒绝、超时能区分；
- 上传失败与发送开始后的失败能够区分；
- 多片段部分成功不会因最后抛错而丢失已成功事实；
- 所有消息共用正确的序号与剩余预算。

参考源码中的 session.send() 会捕获异常并返回 []；因此“await 正常结束”不能判断 success。[S15]
QQ 编码器可能拆分富文本并部分成功后报错；一条应用消息不能默认等于一次平台发送。[S16]

4.3 高层接口不满足时的允许路径

允许在薄插件内部做一个小范围 QQDelivery 适配器，使用官方 QQ adapter 的内部方法，将 upload 和 send 分开：
- 复用官方适配器的登录和鉴权；
- 平台方法签名和返回结构按实际锁定版本确认；
- 图片上传明确禁止自动发出媒体消息，再单独发送；
- 同一入站消息的文字、图片、附文、提示和回退全部走同一个发送协调器；
- 由一个实现管理 msg_seq，不能同时让高层 encoder 和自建代码分别递增；
- 全部内部 API 版本依赖封装在该小适配器中，并建立模拟测试；
- 不 fork 整个 Koishi，不将 QQ SDK 对象传进 Python，也不双开两套生产接收器。

若公共/内部方法均不能满足关键语义，保留现生产入口，继续完成隔离开发，明确报告发送门禁失败；不得以隐藏错误或盲重发来通过验收。

4.4 原始事件、身份与触发门禁

M1 必须从原始 QQ 事件到锁定适配器产生的 Session，再到业务请求进行验证，不能仅手工构造 Session 绕过接收路径：
- 覆盖 GROUP_AT_MESSAGE_CREATE、GROUP_MESSAGE_CREATE 和 C2C_MESSAGE_CREATE，核对群/私聊身份、发送者、原消息 ID、机器人 AppID/selfId 的区别和时间单位。
- 核对实际连接地址、网关地址及事件订阅；保留现有 Taki 所需的网关兼容行为，不能因文档默认值认定已兼容。
- 当前 Taki SDK/夹具使用 group_openid、member_openid/user_openid；所引适配器快照读取 group_id、author.id。两者是否同存或需要窄转换须由锁定包和脱敏实际事件证明；不从测试夹具推断线上格式，不猜造身份或使用公共会话键。
- 检查自身 @、@其他机器人、普通聊天、机器人消息、全角前缀和重复投递。只把符合 Taki 触发条件的内容交给业务；保留 Koishi 功能范围/权限过滤。
- 群许可/拒绝事件可能只通过适配器 internal 事件暴露。验证实际订阅路径，确保事件仅转换一次并传给第 5.3 节通知契约。

缺少真实事件或实机授权时，使用明确标记的固定事件夹具验证适配器源码/安装包路径，并保留实机门禁；不得称其为线上兼容结论。无法识别的身份/格式明确拒绝，记录不含私人标识的错误类别。

4.5 平台能力与 Taki 配置分开

群聊、C2C 的消息身份、回复窗口、上传目标、发送次数分别核对。当前 Taki 的“5 次被动槽位”是源码实现，不能自动当成所有 QQ 场景的有效平台规则。

建立经验证的 capability profile：
- 会话种类；
- 支持的原消息字段和时间单位；
- 有效回复窗口；
- 每条入站消息的发送预算；
- 文本与图片边界；
- 回执/审核处理能力；
- 实际发送路径及其版本。

取平台允许范围、适配器已支持范围和 Taki 配置的共同可用部分；不因平台可能允许更多就自动扩大 Taki 行为。[S19]

初期探针可先做群聊，但完整迁移验收必须覆盖当前实际开放的 C2C 等场景。某个现有入口未通过时，列为未完成或切换阻塞，不静默关闭后宣称全面迁移。

============================================================
5. 本机接口与最小数据契约（待实现）
============================================================

本节接口名为建议，不是现有接口。执行方可适配项目命名，但必须保留以下语义，并记录最终字段和协议版本。

5.1 推荐操作面

- GET /v1/health：进程存活，不等于可查询或 QQ 可用。
- GET /v1/ready：初始化状态、支持协议、后端代码身份、必要依赖/数据可用状态。
- POST /v1/requests：按稳定 request_id 接纳一次查询，返回准备中、已准备或明确终态。
- GET /v1/requests/{request_id}：重取同一次任务状态/结果，不重新执行业务。
- GET /v1/deliveries/{delivery_id}/parts/{part_id}/image：读取该计划已经编码的图片字节。
- POST /v1/deliveries/{delivery_id}/events：报告发送意图、回执、上传失败、终结或取消；具体事件结构固定且校验。

采用同步快速返回或 202 + 有界轮询由实际耗时决定，但必须支持同一请求取回状态。不能让断开的一次 HTTP 连接决定 Python 任务已经被取消。

5.2 请求必须携带

- 协议 major/minor；
- 稳定 request_id；
- 实例身份和机器人应用身份；
- 平台、会话类型、会话 ID、发送者 ID；
- 原始入站消息 ID及原消息时间；
- 去除平台控制元素后的业务正文；
- 经验证的 capability profile 标识；
- 网关运行代次/实例标识，用于停用后的迟到请求隔离。
- 入站顺序元数据：在已登记网关代次内单调递增的 ingress_seq，以及原消息身份；这是接纳/交付所有权元数据，不是客户端构造的业务 generation/lineage。

request_id 应与原事件绑定，而非每次 HTTP 重试随机生成。
后端记录身份与正文摘要；相同 ID、相同内容复用同一次任务，相同 ID、不同内容拒绝。
稳定请求身份与网关运行代次分开：request_id 和业务内容摘要不包含网关代次、发送尝试 ID 或重试时间。这些字段属于交付所有权元数据；重载后同一原事件仍命中原记录，但读取旧记录不授予新代次继续发送的权利。

首次接纳必须保留同会话的入站先后关系。推荐网关先按序完成轻量接纳登记，再并行准备；后端同时记录同会话的接纳高水位，拒绝已越过高水位但此前未接纳的迟到旧请求，返回明确 stale_admission，不执行查询、扣额或清除上下文。同一 request_id 的重复读取先命中原记录，不因较低 ingress_seq 被当成新业务。
接纳响应丢失时只查询/重交同一请求；不能更换序号重新包装。接纳失败/取消的序号可以明确结束，不能让后续请求永久等待；越过后迟到的旧登记不得复活。网关代次必须由后端登记并撤销旧发送/接纳资格；重载后原事件重投仍先按稳定 request_id 去重，不授予新代次旧任务发送权。
正文/身份摘要不包括 ingress_seq、网关代次或发送尝试。原消息时间不能单独替代顺序标识，因为精度相同、时钟差与重投均可能存在。业务 generation/lineage 仍完全由后端生成。

平台会话身份以实际 opaque ID 传递；不假定群用户标识等于私聊用户标识，不把 QQ 号当成官方 openid，不传完整 SDK Session。

缺少建立上下文所需的身份时，按现有边界拒绝建立续查状态；可否处理无状态查询按当前行为确定。不得使用“所有未知用户”这一公共会话键。

5.3 主动通知与群许可接口（与被动查询分开）

以下为 M2 前需固定的逻辑契约，具体路由可以随实现调整；不要求在 M1 冒充已实现后端：
- 网关 → 后端：报告群发现、入群、退群、允许、拒绝事件，携带实例/AppID、群 opaque ID、原事件身份、事件类型、统一单位的事件时间及网关代次。事件去重和新旧比较由后端处理；普通查询不授予主动许可。
- 网关 → 后端：有界领取已提交部署对应的待发通知（可采用 POST /v1/notices/claims）。后端核对部署身份与唯一通知账本，以实例/AppID、群和部署身份生成稳定通知键，返回正文、领取标识、期限和明确的主动发送类型。
- 网关 → 后端：报告 bot_state 权限核验结果及发送意图/结果（可采用 POST /v1/notices/{notice_id}/events）。权限核验关联领取时的群事件版本，不能覆盖随后发生的拒绝/退群事件。
- 主动发送不要求也不伪造原用户 msg_id；不占用或借用被动回复序号、窗口和预算。Koishi 使用官方适配器完成实际权限查询和发送，Python 不接收 QQ 密钥。
- 同一通知只有一个有效领取者。发送前持久记录意图；领取超时、停用、结果不明和迟到 ACK 按第 6 节同等原则处理。已经开始发送的公告不因新网关领取而重发；迟到结果只补记事实，不重开发送权。
- Python 保留唯一通知账本及部署提交门禁，Koishi 不再维护第二套发送完成账本；公告生成继续使用既有独立额度边界。

接口设计在 M2 同步冻结，实际通知接线与验收可在 M4 完成。应覆盖权限撤销与在途查询竞争、领取后重载、发送后 ACK 丢失、相同部署重复领取和旧版本回退。

5.4 后端返回

- request_id、delivery_id、计划版本和支持协议；
- 业务状态：成功、空集合、未知、歧义、数据不可用等，保留原语义；
- 有序 part_id 和片段类型；
- 已生成文字、图片资源标识及 MIME；
- 与同一捕获结果对应的完整备用文字/回退分支；
- 本批预计发送消耗和必要提示预留；
- 原始结果所需的版本信息及不透明上下文票据；
- 准备耗时与可用期限等必要元数据。

Koishi 不接收 QueryContext 的可写内容，不自行生成 generation 或游标；票据只用于关联，不赋予任意写业务状态能力。

业务状态与传输状态分开。来源不可用或用户输入歧义可以形成可发送的正常说明文字；不能将它们统统变成“HTTP 失败，自动重试”。

5.5 图片与文本

- Python 提供已经编码的图片，保留既有字节、尺寸、像素预算。
- 图片接口只解析后端生成的受控标识，检查归属和有效期。
- 不允许请求任意本机路径或让网关指定任意资源下载 URL。
- 结果中的文本以纯文本安全编码交给 Koishi；不当作任意消息标记执行。
- 不在 JSON 中长期缓存大量重复 Base64 图片；图片字节和续发资源统一计入内存/留存预算。
- 总预算覆盖已准备但尚未提交的 requests/deliveries、等待发送及上传中的页、备用分支和 ContextStore 余图；共享字节按实际持有计量，复制出的字节不能漏算。
- 同时限制计划数量与总字节。达到上限时明确拒绝新任务或终结尚未发送的计划并释放资源；不能只依赖 ContextStore 淘汰，因为未确认的准备结果还未进入该存储。
- 切换与回退后，过期图片不能被误用为另一请求的结果。

============================================================
6. 发送、回执、幂等与恢复
============================================================

6.1 三个事实分开

1) 后端生成了结果。
2) 平台接口确认接受了具体消息，并返回有效标识。
3) 后端记录了该回执并按规则提交状态。

它们不是同一个布尔值。平台回执也不代表用户已读；用户实际收到的验收另行记录。

6.2 每个片段的状态

- pending：尚未开始平台发送。
- sending：记录了发送意图，正在尝试平台发送。
- success：取得属于该片段的有效平台消息 ID，且结果无明确错误；需要审核时按已验证路径确认。
- failure：平台明确拒绝，能确定该片段没有成功发送。
- uncertain：发送开始后超时、断线、空回执、进程中断或无法确定的部分成功。
- aborted/expired：未发送部分因取消、停用、窗口或计划过期而结束。

上传状态单独记录，不与 success 混用。fallback_pending 保留为有严格前提的业务转换，见 6.5。

先按一个明确应用片段对应一次可预测 QQ 发送来实现。若编码器仍会拆分，必须细化为能够逐次确认的实际发送单位；不能只看整批最终返回值。

6.3 发送协调

- 全部片段按计划串行发送，同一原消息共用一个次数预算和序号管理者。
- Python 负责生成有序分页及回退内容；Koishi 负责实际发送和总消耗校验。
- 两端不能各自扩页、截断或各算一套完整预算。
- 进度提示、失败提示和溢出提示同样消耗预算；首期不新增无必要的“正在处理”回复。
- 真正发送前再次检查原会话、插件代次、计划有效期、回复窗口和剩余预算。
- 回复超时不得静默退为主动消息。
- 只有一个有效实例持有当前片段的发送权；不得由两个回调同时发同一片段。
- 发生 failure/uncertain 后，按现有边界停止当前批；已经 success 的消息不重发。

每次实际平台发送采用固定次序：后端确认发送意图已记录 → 调用 QQ → 提交结果并取得后端确认 → 才申请下一片段的发送意图。
回执提交的响应丢失时，只查询状态或重交相同回执；既不重发当前片段，也不继续发送后页。平台已成功与后端尚未确认记录的状态不能合并处理。

6.4 回执事件必须可重复提交

回执至少关联：
request_id、delivery_id、计划版本、part_id、send_attempt_id、状态、实际消息 ID、必要的错误分类和时间。

后端必须：
- 校验请求归属、计划、页序和允许的状态转换；
- 重复相同回执不重复推进；
- 冲突回执不覆盖已经确认的事实；
- 迟到/乱序回执不跨过未决片段提交业务上下文；
- 保留已成功片段，不能因后续失败把整批标为“全部没发”；
- 明确 batch_finished / aborted / expired 等终结，释放在途租约；
- 允许仅重试回执记录，不因此重新发送消息。

租约到期、插件停用或批次终结后，旧上下文票据的提交权与未发送页的发送权一并失效。
已经发起的平台调用按真实结果收尾，无法确认则 uncertain；迟到的真实回执仍可幂等补记交付事实，但不得复活旧租约、发下一页、恢复旧任务或覆盖后续续查进度。

6.5 上传失败与备用文字

保留现有区别：
- 上传失败或无有效 file_info，且还没有发起该媒体消息：可以走原捕获结果的备用文字。
- 上传成功但媒体消息发送结果 uncertain：不再补一次文字，不重发媒体。
- 短备用文字：按既有分块/预算发送，确认后按对应逻辑提交。
- 长备用文字：只有“完整文字已保留，请 /继续”提示本身确认 success，才产生 fallback_pending。
- fallback_pending 由 Python 转换成等价于 _fallback_cursor 的状态：先保留本页完整文字分块，再接原有余页，不重查、不丢余页。
- 提示本身 uncertain 时，不可当成 fallback_pending。
- 多段文字的可选择上下文只在原语义要求的完整部分交付后生效，不在第一段成功时提前暴露整份选择结果。

动态回退可以请求后端返回一个有版本的回退分支；不能让 Koishi 自行截正文或再跑一次查询补内容。

6.6 轻量持久记录

跨进程新增了“QQ 已收到、Python 尚未收到回执”的真实窗口。第一版为此增加小型交付记录，建议由单个 Python 进程用 SQLite 管理，不新增数据库服务。

最低记录：
- 请求唯一键和正文/身份摘要；
- 计划、片段、发送尝试与持有者代次；
- 发送意图、结果和消息标识；
- 创建/终结时间及所关联的后端运行代次。

实际发消息前先确认发送意图已记录；记录不可用则不开始新的平台发送。发送意图接口本身须幂等，不能因其响应丢失重复授权发送。
发送许可绑定唯一 holder、网关运行代次与 send_attempt_id；重复提交只查询/确认同一次尝试，不生成第二份可执行许可。Koishi 侧对同一次尝试也须保证单一发送执行者。

只保存必要元数据；完整会话、密钥、图片二进制和游戏资料不塞入该表。续查上下文与余图仍可保持现有有界内存状态，不要求跨重启恢复。

恢复规则：
- sending 但无确定结果：视为 uncertain，不自动重发。
- 平台已成功但回执提交未获后端确认：查询或重复提交同一 ACK，不重新发送；后端若已记录 success，返回已有事实而不重复推进。上下文已丢失或租约已终结时，只记录交付事实，不重建旧上下文。
- 已准备但运行期图片/游标已失效：明确返回过期，要求用户重新查询。
- 插件重新加载后不能接管并重发旧实例已经开始的片段。
- 同一原事件重投命中记录时，返回原状态，不重新扣额、重跑和重发。
- 记录留存/清理有容量与期限，覆盖已验证的重投窗口和任务生命周期；进行中或未决记录不能被普通淘汰直接忘记。
- 记录已过保留边界时，不声称还具备去重保证；过期旧事件采用已记录的拒绝/重查策略。

承诺范围：有界幂等、确认后推进、结果不确定时不盲重发。
不得承诺 exactly-once、任意崩溃后无损自动续发或用户必然收到。

============================================================
7. 续查、图文一致与原有产品语义
============================================================

7.1 上下文和代次

Python 继续持有 ContextStore 等价实现：
- 第一版每个后端只绑定一个已配置的实例身份与机器人应用身份，并拒绝不匹配请求；这两个身份形成 ContextStore、请求与资源记录的存储命名空间。当前四元会话键只能在该命名空间内复用，不能仅接收身份字段而不落实隔离。
- 同一请求首次业务接纳时按第 5.2 节验证入站顺序后开启新查询代次；HTTP 重试不重复 begin。未接纳的迟到旧请求不得清除较新上下文；两个续查的接纳顺序同样受约束。
- 新完整查询清除旧可选上下文的时点保持当前语义。
- 续查到达时捕获 lineage，真正执行前核对。
- 同用户续查串行范围覆盖“准备—等待发送—回执推进或终结”，不能只锁一次 HTTP prepare。
- 新完整查询可以建立新 generation；旧查询/旧 ACK 不得覆盖它。
- SDK Session 不进入上下文存储。
- TTL、容量、图像留存和版本失效行为基于现行配置保留。
- 超时、取消、卸载和对端失联都有租约终结，不能永久锁住用户；终结同时撤销旧票据的业务提交权，迟到交付事实按 6.4 记录。
- 客户端不得提交自己构造的 generation、lineage 或任意 context。

7.2 /继续 的语义

- 发送同次捕获并已编码的剩余结果，不重新抓一份数据生成“看似下一页”。
- 按已确认的实际进度推进；不能因为计划生成完成就标“全部发送”。
- 不确定页按现有策略拒绝盲目续发并引导重新查询。
- 保留资料与昵称版本校验；具体失败文案沿用既有语义。
- 仅重启后端导致的运行期上下文丢失，要明确表现为上下文失效。

7.3 图文和来源

- 文本、图片、选择序号与备用文字使用同次捕获结果。
- 上传失败不得通过再次调用查询器生成替代答案。
- 来源不可用、未知、缺失、歧义、不适用和真零继续区分。
- 保留当前来源选择和不跨源补造规则。
- 不将“加一个 snapshot_id 字段”当成已经实现全仓原子快照；只声明实际冻结/捕获的范围。
- 绘图现存资料补全依赖不要求本次全部清除；只提取迁移确实触及的编排。

7.4 命令入口与其他插件共存

- 保留现有命令、前缀处理、别名、语言、参数和多命令拆分语义。
- Koishi 只做必要入口识别与平台元素处理，业务正文交原 Python 解析。
- 只处理应触发 Taki 的消息，不把普通群聊或其他机器人的消息送入 /问。
- 未识别为 Taki 请求的消息正常交给后续插件。
- 如果使用 middleware 路由，也必须真实执行对应的群范围/权限检查，不能绕过 Koishi 管理。
- 明确帮助及重名命令的处理；默认保留当前公开 Taki 入口，不以迁移强迫用户更换整套语法。
- 同一消息多命令仍按原顺序输出，共用一份原消息发送预算。
- 多命令不是依赖链，“先查列表再在同一消息选择”仍按当前边界处理。
- 多列表不悄悄选一个作为默认上下文；整批余图与可选择查询上下文分开。

============================================================
8. 生命周期、容量、配置与故障边界
============================================================

8.1 Python 后端

- 增加独立启动模式，正常初始化资料后才 ready。
- 不要求 QQ 密钥，不导入 botpy/platforms.qq 即可运行核心查询与渲染。
- 过渡期安装包可保留旧 QQ 入口及依赖；不以删除依赖作为迁移第一步。
- 每个实例只组装一份 repository、AI parser、额度管理和 ContextStore。
- 明确启动和停止主资料刷新、属性刷新、HistorySampler。
- 保留前台查询与后台采样既有的让行、退避和缓存语义。
- QueryGate 继续限制真正未结束的工作，HTTP 断开不立刻释放还在运行的线程容量。
- 业务超时可以使结果失效，但不能宣称杀掉了正在运行的 Python 线程。
- 关闭时先停止接纳，终结或排空在途请求，处理发送租约，再停止后台任务。
- 保持既有 Python 3.10/3.12 门禁；确需变更版本范围时单独给出原因和兼容影响。

8.2 Koishi 插件

- 使用当前版本支持的服务依赖和生命周期管理。[S17]
- 初次加载验证后端协议；后端未 ready 时给明确可恢复状态。
- dispose 后不再接纳新请求、不再轮询取新结果、不再启动新的平台发送。
- 未开始发送的任务可以 aborted 并释放发送权；已发出的 QQ 请求不能凭本地取消认定未被平台接受，保留尝试记录并按确定结果或 uncertain 收尾，不重新授权发送。
- 取消 HTTP 等待与取消 Python 工作分别处理。
- 每次插件实例有运行代次；迟到回调须检查代次及发送权。代次过期禁止新发送和旧业务提交，但不禁止幂等记录已经发生的真实交付事实。
- 不在热重载中重复启动 Python 后端、资料刷新或采样。
- QQ 平台发送的自动重试策略显式设置并记录；不得靠默认值重放整条消息。
- 普通查询 HTTP 重试、资源读取、QQ 上传、QQ 发消息和业务 ACK 重试分别定义。

8.3 配置归属

Python：现有来源、缓存/历史路径、AI 参数与额度、准备并发、采样、业务状态。
Koishi：QQ 接入凭据、Taki 插件功能范围、后端地址与认证、协议超时、发送策略。
共享：实例身份、协议版本、经验证 capability profile 标识。
同一参数只有一个权威管理者，不让两端分别维护不同的 AI 配额或分页规则。

本机接口默认仅监听 loopback，使用实例级认证；图片和交付接口同样检查身份。
不把 QQ 密钥交给 Python 查询后端，也不把 AI 密钥复制进无此职责的插件配置。
日志用 request_id 等关联，避免输出凭据、完整事件和原始私人标识。

8.4 资源验收

记录同一数据快照与查询条件下：
- 冷启动到 ready；
- 文字查询、单图、典型多图的准备及交付耗时；
- Python 与 Koishi 各自及合计的空闲/峰值内存；
- 队列饱和时是否有界；
- 取消后的线程容量是否仍被正确占用；
- 准备完成却因排序等待而积压的计划是否也计入总数量/字节上限；
- 图片、备用分支和 ContextStore 之间是否漏算实际内存，资源与交付记录清理是否有效。

不要预先承诺现有机器一定足够，也不要把跨进程开销说成零。若退化明显，先定位序列等待、编码复制、重复资料初始化等具体原因，不先增加服务或机器。

9. 数据、后台任务、通知与部署归属
============================================================

9.1 单写者表

正式切换前在任务记录填写以下每项的当前路径、目标管理者、停止/启动时点、兼容与备份方式：
- 主资料与来源专项缓存；
- 图片/素材缓存；
- AI 额度和查询指标；
- 榜单历史 SQLite；
- 续查/余图内存状态；
- 新增交付记录；
- 更新通知账本与群许可状态；
- 更新器事务和当前版本身份。

新旧完整实例不得同时写同一路径。对照验证使用固定公开夹具、捕获结果或独立数据目录；不要用真实生产缓存做双写试验。

9.2 更新通知

保留报告生成、已提交部署身份核对和账本的业务规则。平台相关部分按第 5.3 节主动通知/群许可契约经窄接口接入 Koishi：
- 群发现、入群、退群、允许和拒绝事件保持准确语义；
- 发现群不等于获得主动通知许可；
- 通知发送仍独立于被动查询，不能伪造原消息上下文；
- 不因插件加载、普通重启或后端 ready 而重新发公告；
- 只有完整部署事务达到既有通知条件才考虑公告；
- 不确定送达不盲重发；公告 AI 调用不挪用群友查询额度。

正式切换需要覆盖原来已启用的通知功能；暂时缺少该项时明确为切换缺口，不在旧 QQ 入口停止后悄悄丢失。
菜单/指令面板的实际变更作为独立操作核对，不把本地命令注册等同于 QQ 控制台更新。

9.3 发布、健康与回退

同一发布提交应明确 Python 与 Koishi 插件的兼容组合。可以分别打包，但组合清单至少记录：
- 仓库提交；
- Python 产物摘要；
- Koishi/插件产物与依赖锁摘要；
- Node 与平台适配器实际版本；
- 协议兼容范围；
- 运行配置/数据迁移版本及回退限制。

优先保留现有 Python 离线产物流程，为 Node 部分增加可重复的构建与安装验证。
不得在生产定时更新时解析 latest 或临时联网安装浮动依赖。
现有 updater、离线包校验、共享数据兼容及候选准备约束都需认真接入，不用删除检查来通过。

新健康条件至少包括：
- 后端进程和资料初始化可用；
- Koishi 与目标 QQ 账号连接状态；
- Taki 插件到后端的协议/版本握手；
- 必要的离线组合探针；
- 生产验收中单独记录的真实图文查询。

不再用伪造旧“ournotes_bot.qq 已上线”日志替代上述判断。

受信更新控制器、launcher 和 systemd 定义的修改先形成可审阅补丁、安装说明与恢复包。按实际授权单独安装；main 合并不代表已安装控制器改变。不得让应用候选自行替换受信控制器。[S11][S12]

开发阶段保持当前 bot 模式及默认配置兼容，新增接入默认不自动接管生产。main 可能自动部署，不能把提交/合并与上线影响分开忽略。

10. 实施里程碑
============================================================

按依赖顺序推进，可以分提交/PR；里程碑不是重复申请普通开发许可的节点。

M0：基线与兼容目标
- 确认仓库、工作区改动、规则、当前已开放功能与配置。
- 记录与本文基线的相关差异。
- 定位现有测试和 CI；记录真实运行结果，不照抄本文。
- 锁定候选 Koishi/Node/QQ adapter 安装组合。
- 固定群/C2C 能力矩阵与命令样本。
产物：基线记录、版本锁、行为对照清单。

M1：完整入站与发送端最小探针
- 在隔离环境建立本地薄插件与 QQDelivery 适配。
- 从固定原始群聊/C2C 事件进入实际安装的适配器，验证 Session 身份、消息 ID、时间和触发过滤；检查连接地址、订阅及群许可事件。
- 使用固定图片/文字验证原会话、序号、调用次数、真实回执/模拟回执。
- 验证上传失败、第二片段失败、空回执、超时与重复事件。
- 高层接口不满足时按第 4 节选择窄内部适配。
- 有已授权测试机器人时补真实验证；没有时明确保留该门禁。
产物：发送适配、版本行为测试和实机待验项。
退出条件：选定实现能正确处理已声明事件夹具的身份、触发与发送阶段；不靠手工 Session 绕过接收、不靠吞错通过。安装包探针与实机证据分列；实机未通过不得进入生产切换。

M2：共享应用层与常驻后端
- 从 qq.py 小范围提取准备与业务协调，复用 reply_preparation。
- 旧 QQ 入口继续调用共享逻辑。
- 增加后端启动、HTTP 契约、单实例对象和有界队列；同时固定入站顺序/代次登记和主动通知的通信契约。
- 接入运行期上下文、请求幂等及轻量交付记录。
- 后端无需 QQ 凭据即可跑通核心样本。
产物：常驻后端、接口说明、旧入口回归结果。

M3：完整查询与交付接通
- 接入现有命令、别名、帮助、多命令与 /问。
- 接通逐片段发送、回执、失败回退、多图 /继续、选择和分页续查。
- 保留来源、版本和图文一致语义。
- 验证插件停用、HTTP 中断、ACK 丢失、并发及迟到代次。
产物：完整集成路径及验收矩阵。
退出条件：当前已开放查询行为均有对照结果，关键失败场景通过。

M4：运行任务与发布准备
- 后端接管刷新、属性与采样，通知完成平台接线。
- 完成配置归属、数据路径、单写者和共享数据兼容说明。
- 形成两个进程的启动/停止、健康与组合版本发布方案。
- 调整相关 CI/发布产物验证，准备控制器补丁和回退包。
- 用隔离环境验证升级、失败恢复和回退。
产物：可审阅发布组合、切换 runbook、恢复包与实际验证记录。

M5：目标环境切换与验收
- 只在已有授权和必要实机门禁满足时执行。
- 先测试机器人/测试范围，再切换正式实例；同一原请求只有一个接收/回复路径。
- 未切换的旧生产入口保持正常；不靠同 AppID 双开来假设灰度隔离。
- 记录真实代码、进程、协议、平台回执、用户可见结果与后台任务证据。
- 观察后恢复正常受管更新节奏。
产物：上线与回退验收记录，或精确列出的外部阻塞项。

11. 验收矩阵
============================================================

下表是必要验证目标，不要求为每行新建一个测试文件。优先复用有价值的现有夹具与测试。

A01 无 QQ 后端：
清空 QQ 凭据、禁止导入 QQ SDK，固定资料下查询及绘图可运行；后端状态不冒充 QQ 就绪。

A02 原命令：
当前已开放命令、别名、语言、参数、多命令拆分与结果语义对照一致；普通聊天不被截获。

A03 /问：
本地可解问题不调模型；受限模型输入经过原校验；测试用 mock，无真实付费调用。

A04 图文同源：
文字、图片、序号、备用文字来源于同次捕获结果；不因上传失败或续发再次选不同数据。

A05 单图成功：
使用正确原会话与目标接口，实际消息 ID可归属该片段；确认前上下文不推进。

A06 两片段顺序：
同一原消息序号不冲突、次数消耗正确、原顺序交付；图片附文是否额外拆消息有证据。

A07 部分成功：
第一片段成功、第二片段失败或 uncertain，第一片段保留；不重发第一片段、不越过第二片段推进。

A08 上传失败短文：
上传阶段失败但尚未发送媒体，备用文字完整且计入预算；确认后才按对应语义提交。

A09 上传失败长文：
提示确认成功才建立 fallback_pending；/继续 先发完整备用文字，再衔接原余页。

A10 媒体发送不确定：
上传成功、发消息超时/空回执，不补文字、不重发媒体，游标采取明确不确定策略。

A11 请求重复：
同一事件或同 request_id 重试只复用一次准备；不重复 begin、扣额、查询或交付。
同 ID 不同正文/身份明确拒绝。
网关重载改变运行代次不会把同一原事件变成新业务请求，也不会取得旧发送权。

A12 回执重复/丢失：
重复 ACK 不重复推进；ACK 响应丢失只查询或重交记录；后端确认前不能发送下一片段，更不能重发当前片段。
发送意图的重复请求不会产生两个可执行许可；同一次尝试只有一个发送执行者。

A13 进程重启：
发送意图之后、发送确认之前的中断不会触发自动整批重放。
恢复记录与已经失效的内存上下文分开。

A14 续查代次：
旧完整查询迟到、旧 ACK、旧 lineage 不覆盖新查询；同用户连续续查串行不串页。
租约过期后迟到回执只补记交付事实，不复活上下文提交权或覆盖之后的续查进度。

A15 多用户/多机器人：
相同显示名称、跨群、群与私聊、不同实例之间不串上下文；身份缺失不共用公共状态。

A16 多命令和溢出：
整条入站消息共用发送预算；保持原顺序和必要提示预留；多列表无错误默认选择上下文。

A17 超时与容量：
忙时有界；取消 HTTP 后运行线程仍正确占容量；旧任务完成不再自动发过期结果。
排序等待中的已准备多图、上传页、备用分支和 ContextStore 余图共同受数量/字节上限约束，达到上限有明确处理。

A18 热卸载：
dispose 后不再启动新的平台发送，新实例不重复发送旧任务；本地等待、排序票号和业务租约按有界流程终结。
未开始发送的任务可 aborted；已发出 QQ 请求的尝试保留记录，无法确认时转 uncertain，不重新授权发送。
迟到真实结果仍可幂等记录交付事实，但不得启动下一片段、恢复旧任务或推进新代次的业务上下文。

A19 回复窗口/预算：
群与 C2C 分别验证；到期不退化成主动发送；必要提示/回退都算在实际预算中。

A20 后台任务：
每类任务只启动一次，Koishi 热重载不重复采样；数据/来源故障沿用原退避与降级边界。

A21 通知：
群发现不等于许可；不因加载或重启重发公告；通知仅关联已提交部署；不动独立翻译机器人。

A22 发布回退：
协议不兼容的组合明确拒绝；候选准备失败不切旧服务；切换失败能按操作包恢复。
代码回退不误称数据也已回退。

A23 持久化兼容：
当前与回退版本可读取需共享的既有缓存/额度/历史/通知数据；新增交付记录有版本和边界。

A24 API 访问边界：
未认证调用、跨实例资源、任意路径、错误票据、乱序/冲突事件和超大输入均被明确拒绝。

A25 实际交付：
分别记录本地测试、CI、构建产物、目标进程采用版本、QQ 回执和用户实际看到的结果。
仅在真实环境验收后标记该层通过。

A26 接纳乱序：
网关 A→B、HTTP B→A 时，迟到 A 不覆盖 B；即使实际发送顺序 A→B，也必须保留 B 的上下文。覆盖旧请求首次登记迟到、响应丢失后的重试、两个续查逆序、取消缺号及关闭发送排序。

A27 原始入站事件：
使用锁定适配器的实际解码路径核验群/C2C 身份、消息 ID、时间、触发和重投；兼容夹具与真实事件分列。普通聊天、@其他机器人、缺失/冲突身份不建立错误上下文；不以发送函数通过代替接收通过。

A28 主动通知跨进程：
权限事件去重/新旧判定、唯一领取、部署提交门禁、发送意图、ACK 丢失及网关重载均有验证；不伪造被动上下文、不产生第二套账本、不在未知送达时重复公告。

12. 生产切换与回退操作包应包含什么
============================================================

12.1 切换前

- 记录当前生产真实代码、控制器、服务、数据路径和启用功能，不能只看源码 HEAD。
- 核对当前更新事务，按既有锁和定时器流程安排窗口，不打断进行中的切换。
- 准备并验证新版本组合、配置、共享数据兼容及可读备份。
- 确认后端接口仅在预期范围可达，QQ 接入方式在目标应用可用。
- 明确旧入口停止到新入口接管的时间顺序；单写者在切换中仍成立。
- 说明正在进行的查询、旧上下文、余图和未决发送会如何处理。
- 真实测试和生产动作未获授权时，先交付以上完整材料再请求最后所需决定。

12.2 切换时

- 阻止新请求进入待停止路径，按有界时间排空或终结任务。
- 停止旧 QQ 完整运行时，确认不再共同写业务数据。
- 按受管流程启动对应 Python 后端及 Koishi 组合。
- 确认后端 ready、协议一致、QQ 连接和 Taki 插件可用。
- 通过已授权真实查询验证文字、图片、续查与关键边界。
- 核对刷新/采样实际运行、历史时间戳和通知状态。
- 成功后才完成部署状态提交；公告仍按原许可和账本规则处理。

12.3 失败回退

- 任一关键门禁失败时，停止新入口接收和发送，终结未决发送权。
- 保存诊断所需的最小状态，不清空额度、历史、失败记录或发送记录来重试。
- 恢复已验证的旧代码/运行配置/控制器组合，确认只有一个旧运行时写业务数据。
- 保留仍兼容的共享数据；确需数据恢复时使用已审阅的对应恢复步骤。
- 不重放未确认发送，不把代码回退当成游标和消息历史全部恢复。
- 用相同层级证据确认旧入口可用，再恢复更新调度。
- 若恢复失败，明确报告实际状态和人工恢复路径，不能写“自动回退已成功”。

============================================================
