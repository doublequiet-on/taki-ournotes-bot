# GEB 使用与维护指南

本文用于后续修复、功能开发、文件整理与文档维护，帮助开发者和 Agent 把实现变化同步到正确的架构层。它不授权重构、安装、联网或部署，也不替代 [AGENTS](../AGENTS.md) 的开发与安全规则。

核心方法：**从上往下定位任务，从实现往上检查影响，只更新事实发生变化的层。** 代码、配置与测试用于确认当前行为；文档负责解释边界和导航，历史草案不作为第二套当前事实。

## 1. 每一层维护什么

| 入口／层级 | 维护内容 | 不应写入 |
|---|---|---|
| [AGENTS](../AGENTS.md) | 开发入口、权限与生产安全边界 | 每个模块的实现清单、每次任务流水账 |
| [L1](../L1.md) | 仓库区域、系统级流向、外部状态、文档所有权及 L2 路由 | 函数细节、完整字段表、测试通过数量 |
| L2 | 域或目录的职责与非职责、跨域契约、依赖、副作用、失败边界及下层入口 | 全部源码复述、另一份操作手册 |
| L2-2 | 稳定子能力的流程、兄弟边界、实现文件归属和相关测试 | 为每个文件机械增设一层、重复上层总览 |
| L3 | 文件头的输入、输出、归属与重要副作用／依赖 | 长篇算法解释、历史改动记录或独立 L3 总表 |
| [DEV_GUIDE](DEV_GUIDE.md) | 按任务定位源码、关键符号和验证命令 | 重复维护整套架构与所有业务规格 |

从 L1 选择现有地图，不要求物理目录与逻辑域一一对应。包根文件可以归属相应源码域；跨域消费的类型仍由其职责所有者维护，不因为“共享”就新建公共模块。

## 2. 开始任务：先定位再修改

1. 读取适用 AGENTS，确认真实仓库根目录、当前分支及工作树，区分用户已有修改、本次目标与生产运行状态。
2. 明确目标、允许修改的范围、交付物和验收方式。仅要求审查或诊断时，不自动实施修复；遇到必须扩大范围的改动先说明。
3. 通过 L1 进入相关 L2；需要理解子能力时再进入 L2-2，然后阅读目标文件的 L3、实际实现与相关测试。使用文件名、符号和关键词搜索，不默认阅读全仓。
4. 沿调用方和直接依赖核对关键契约：返回值、异常、状态读写、网络调用、并发、缓存与降级行为。L3 的“只读”不能仅凭函数名或注释判断。
5. 用简短计划说明准备改哪些实现、可能影响哪些地图、如何验证，再动手。若地图与实现冲突，先确定是文档过时还是代码违背需求，不以旧日期为理由删除产品要求。

具体源码与测试的任务映射使用 [开发导航](DEV_GUIDE.md#任务导航)，测试分组使用 [Tests L2](../tests/L2.md)，不在本文再复制一份文件目录。

## 3. 完成改动：按影响选择更新层级

“检查上层”不等于“修改所有上层”。逐级判断事实是否变化，没有变化就保持原文，不追加“本次已检查”等记录。

| 改动情形 | 需要核对／更新的内容 |
|---|---|
| 修复局部算法，输入输出、归属和副作用均未变 | 更新实现和相关测试；核对 L3 准确即可，不为制造文档 diff 改 L2／L1。 |
| 参数、返回值、异常、网络／文件副作用变化 | 先更新 L3；若影响子能力流程或跨域契约，再更新所属 L2-2／L2 及消费者说明。 |
| 新增实现文件 | 按现有职责选位置，补合适的 L3，在直接所属地图加入文件入口和测试导航；只在引入新子能力或顶层区域时向上扩展地图。 |
| 移动、重命名或删除文件 | 核对 import、动态模块名、测试 patch 字符串、资源路径和脚本调用；同步 L3 的 Pos、地图成员与双向导航，按实际位置修正相对链接。 |
| 调整职责、跨域依赖、持久状态或失败边界 | 更新相应 L2-2／L2 和契约的唯一所有者；若改变系统级流向、外部系统或仓库区域，再更新 L1。 |
| 新增／调整测试、工具、配置或文档 | 维护所属目录导航与 DEV_GUIDE 中确实变化的任务入口；参数和依赖以实际配置声明为准，不为非源码文件强加 L3。 |
| 用户命令、操作步骤、数据来源变化 | 同步对应权威专项文档；架构地图只保留职责摘要和链接。 |

例如：只修正歌曲筛选中的一个比较条件，且契约未变，通常不需改 Query L2；若新增筛选能力或改变结果完整度语义，则核对文件 L3、确定性查询 L2-2、Query 契约及图文消费者。只有仓库级路由或系统边界改变才改 L1。

## 4. 如何编写与维护 L3

沿用现有文件头格式，描述实现事实，不写愿景或未经验证的保证：

```python
# L3
# Input: 外部提供的参数、配置、数据或状态。
# Output: 实际返回值、可观察输出及重要异常／终态。
# Pos: 所属职责与本文件作用；见相对路径下的直接地图或机制专题。
# Effects/Dependencies: 网络、文件、缓存、进程、平台调用及关键依赖；注明必要条件。
```

- 修改接口或副作用时同步文件头；不能用“无副作用”掩盖依赖内部的惰性联网或文件读取。
- 保留原有编码、BOM、shebang／编码声明、模块 docstring、future import 和脚本参数块的语法要求。PowerShell 注释位于 `[CmdletBinding()]`／参数块之前；不要为统一注释语言改变原文件编码。
- 最小包入口沿用简短 Pos／Effects 坐标，不为了凑字段加入业务导入。脚本的外部副作用应明确写出；配置、测试样例和普通 Markdown 不机械套用源码模板。
- 文件级坐标只在文件头维护；地图链接该文件，不另建需要实时同步的 L3 副本。

## 5. 新增层级与移动文件的边界

先复用现有职责：目录变大本身不是拆分理由。只有出现稳定、可独立说明的子能力，且需要明确其流程、文件归属或兄弟边界时，才考虑增加 L2-2；新的顶层职责或独立目录入口才需要评估 L2 与 L1 路由。

当前 Deploy、Tests、Docs 使用简短目录地图，Scripts 连接运维工具与视觉验收，不应把同目录文件视为同一业务域。Operations 是跨目录主题，不为文档形式另造源码目录或父子层级。

文件移动只在任务明确包含整理时执行，不因维护地图顺手迁移四个根枢纽或抽取共享契约。获准移动后：

1. 确认旧／新位置、调用者和验收基线，按可验证的小批实施。
2. 保留资源定位、导入时机、公共类型身份、日志通道和运行数据生命周期；不能只修静态 import。
3. 同步文件坐标、父地图、调用方和测试；涉及安装或启动路径时核对打包声明与部署说明。
4. 在 [文件移动历史](../文件移动历史.md) 记录旧／新位置、用途、关联修改及验证边界。仅新增文档或吸收内容应如实标明，不伪称文件移动。

历史设计、发布报告和已执行指南保留原时点语境；必要时加当前入口，不改写历史结果，也不把旧方案再次当作执行清单。正式仓库导航不得依赖旁边的工作区草稿或本机绝对路径。

## 6. 专项文档的信息归属

用户能力和用法放在 [README](../README.md)；验证命令放在 [DEV_GUIDE](DEV_GUIDE.md#开发与验证命令)；来源与素材边界放在 [THIRD_PARTY](../THIRD_PARTY.md)。新增专题登记到 [Docs L2](L2.md)，只在有直接调用或阅读关系的入口补链接。

修改更新或通知相关内容时，按以下分工同步，不复制多份状态协议：

- [自动更新说明](../自动更新说明.md)：命令、启停、恢复、人工验收与排查步骤。
- [Scripts L2](../scripts/L2.md#部署状态协议)：更新工具与共享部署状态的写入／恢复协议。
- [更新通知机制](更新通知机制.md)：公告读者的触发、账本、许可、占位、去重和失败边界。
- [Deploy L2](../deploy/L2.md)：本地准备、启动分流与环境连接。

阶段状态和未验证项进入交接文档，详细过程进入适用的项目日志；仅在节点或状态变化时更新，不往每份长期地图追加任务记录。文档存在于 Git 仓库不等于随发行包提供，发行包收录另按 [MANIFEST.in](../MANIFEST.in) 检查。

## 7. 验证、提交与交付

验证强度随影响范围决定，执行命令以开发导航为准：

- 纯文档／文件头修改：检查实际文件、相对路径、锚点、符号及职责一致性，检查限定 diff；注释改动还需确认编码、语法和非注释正文未变。不为文档检查启动机器人或同步。
- 局部实现修改：运行目标测试及必要调用方测试；公共接口、缓存格式、平台边界或部署流程变化时扩大验证，必要时运行完整离线回归。
- 路径／打包修改：核对动态引用、源码与安装资源路径、发布包内容；需要时进行隔离构建与安装验证。离线样图、真实素材验收和实际 QQ 送达分别记录，不能互相替代。

提交前逐项确认：

- [ ] 实现和测试覆盖当前目标；未改变的接口与安全边界仍成立。
- [ ] 已沿 L3 → 所属 L2-2／L2 → L1 检查影响，仅修改事实变化的层，并同步必要专项文档。
- [ ] 新文件已读取检查；没有新增断链、错误锚点、旧活动路径或工作区外导航依赖。
- [ ] 查看暂存区实际 diff，确认删除与新增是否为预期移动；不默认把用户其他未提交编辑一起提交。
- [ ] 凭据、运行数据、缓存、日志、预览图片、构建产物及工作区历史材料未误入提交；不强行添加忽略文件。
- [ ] 已运行、未执行、失败或受阻的验证分别写清；历史通过记录不冒充当前结果，CI 必须对应本次提交。
- [ ] 用户授权后才提交／推送或创建 PR；提交文档不等于批准合并 main、安装菜单、重启或部署。

交付时简述：改动范围、涉及的 GEB 层与专项文档、实际验证及限制、保留的用户修改，以及提交／PR 状态。目标与必要验证满足后停止，不继续无目的扩层或重构。
