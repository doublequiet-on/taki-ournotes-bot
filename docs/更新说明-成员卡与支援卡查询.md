# 角色卡与 SNAP 查询

## 用法与规则

条件查询是图鉴列表，即使只有一张也不变成详情。先计算全部结果、按对象 ID 去重，再按稀有度数字降序、ID升序分页（沿用原排序）。每页16张，显示完整总数、当前范围、总页数与下一页指令。现有 QQ 回复每次上传一张图片，大结果需要逐页获取，不自动多图或合并转发。

```text
/查卡
/查卡 SSR 颜色=黄色,蓝色 乐队=MyGO 角色=tmr
/查卡 LIVE=分数提升 击奏=JUST
/查卡 得意=MyGO
/查卡 页2
/查SNAP EX
/查支援卡 角色=tmr,skk 乐队=MyGO LIVE=技能延长
/查SNAP LIVE=LIFE回复 击奏=JUST
/查卡 51
/查SNAP 61
/查卡面 51
/查支援卡面 51
/问 MyGO的红色SSR角色卡有哪些
/问 角色=tmr LIVE=技能延长的SNAP有哪些
```

`/查卡`、`/查角色卡`、`/card` 指角色卡；`/查支援卡`、`/查SNAP`、`/support` 指 SNAP。纯数字或 `ID=51` 精确查询该对象的卡牌 ID，不使用角色 ID、资源 ID 或列表序号。无对象的自然语言 ID 同时命中两类时要求明确对象；未知 ID 不改查其他对象。

`/查卡面 ID`、`/查支援卡面 ID` 只输出对应公开 full 卡面，保持比例。当前未核实其他可选版本，不能指定觉醒前后。没有明确 ID 时提示先查列表；缺图退文字，不换其他卡。

不同维度 AND，同维度多个值（逗号、或、竖线）OR；角色任意包含，乐队另行判断。`得意=` 多标签要求全部包含，仅角色卡支持。全部、不限表示该维度不限制。未知值、未核实分类、不完整索引明确提示，不当作不限。带空格的名称建议写成 `乐队=Ave Mujica`；多个命名条件之间加空格。旧二/三/四星输入保留为 R/SR/SSR 别名，新输出使用稀有度名称，不套用其他游戏星级框。

## 字段映射与核实依据

2026-09-28 核对 Project Yume 60张角色卡、62张 SNAP 的公开列表及对应详情；这是调查快照，不代表永远完整的游戏卡池。基址 `https://bdon.yatta.moe/Resources/en/MasterParsed/`，en 是资源目录，不据此判断服务器。

| 原始字段 | 核实依据 | 内部值及显示 |
|---|---|---|
| rarity | 网站 useFilter-BIvyqgQJ.js 映射到 RarityR/SR/SSR/EX 图片；实际列表交叉核对 | R=2、SR=3、SSR=4；SNAP EX=10。2026-10-04已通过生日卡64及Haneoka/Yume两源核实成员BD=20，详见THIRD_PARTY。 |
| attribute | NonoCard-aiXKXz-b.js 引用 /images/CardType{N}.webp，逐张检查实际图标 | 1红（日轮）、2蓝（星球）、3绿（流星）、4黄（闪光）、5紫（月亮）。这些是中文颜色别名，正式属性名称未核实。 |
| character / characters | 关联 characters.json 的 ID，再读 band 并用 refs.musicTags 解析乐队名 | 保留多人及多乐队；舞台名/本名沿用昵称库，不识图猜角色。 |
| 成员 musicTags | 列表 refs.musicTags、详情同名标签，网站称 Favorite Songs | catalog.tags；得意乐曲，多选全部包含。不用该字段猜角色所属乐队。 |
| skills[].type | 成员 leaderSkill/liveSkill/gekisouSkill；SNAP supportSkill/gekisouSupportSkill | 队长、LIVE技能、击奏技能 / LIVE支援、击奏支援分别展示。 |
| LIVE 分类 | 日文原名确定前缀 スコアUP、LIFE回復、判定サポート/判定強化、ライブスキル延長 | 分数提升、LIFE回复、判定强化、技能延长；最后一种目前仅 SNAP。未知名称保留未知。 |
| 击奏分类 | 击奏技能原名 JUST/COMBO/LUCK 前缀，允许前置 撃奏 | JUST、COMBO、LUCK，不从 LIVE 文案中的同名词推断。 |

真实样例：成员51的「スコアUP(LIFEボーナス)」仍是分数提升，不能因 LIFE 字样改成回复。SNAP61、70各有技能延长和LIFE回复两项 LIVE 支援，没有击奏支援。EX 的 icon_skill_scoreup 甚至用于技能延长，所以没有用图标名代替机制分类。同维度保留多分类；明确技能数组中没有该类技能显示“不适用”，旧缓存未获取、新枚举未确认分别说明。

## 完整文案与数值状态

技能默认 Lv.5，采用上游对应语言 effects 占位参数，保留换行、条件、持续时间、范围、概率；支持已给的 multiply/divide/format。不调用 AI 翻译。中文缺失时使用日文/英文并标注，未知参数不补造。

statsMax 不直接当作实际培养数值。本轮仅展示可复现的 Lv.1、Rank 1、成员觉醒0次属性状态，依据网站 cardSkill-B40radPu.js：成员各项为 floor((levelGroup[0].stats + rankGroup[0].stats或0) * statsMax / 10000)；SNAP 为 floor(levelGroup[0].stats * statsMax / 10000) / 100（%）。这只复现资料站属性展示，不实现算分/配队。输入不完整或非有限时不展示培养数值。技能Lv.5与属性示例分别标注，不代表玩家库存。

## 图片与素材限制

卡面来自 Resources/en/Assets/AddressableResources 下 MemberCard/{id}/member_{thumbnail,full}.webp 和 SupportCard/{id}/snap_{thumbnail,full}.webp。实际缩略图分别384×512、512×288。类型图标使用 /images/CardType1.webp 至 CardType5.webp，保留透明通道。

未找到可核实的原生稀有度框索引。成员条件列表采用SSR渐变彩框、SR金黄框、R蓝框，取消文字角标，框内以渐变信息层显示队长/演出/激奏数值及条件，框外保留ID。三列网格每页16张，单个结果仍是列表；SNAP使用同主题横向网格，稀有度框只包卡面，独立浅蓝技能区展示Lv.5基础效果类型与数值，保留触发次数和上限，条件加成见详情；外层主题框包住卡面、技能和ID；EX保留独立标记，使用参考截图中的薄荷绿至冰青边框；角色SSR与SNAP SSR分别按截图色序绘制渐变。框体不宣称为官方素材。无玩家等级、红点或锁定，卡图保持比例，缺图不代用其他卡。成员ID详情使用完整full卡面与同款稀有度框，资料、属性、队长/演出/激奏技能分别成区；所有完整技能文本保留，长文动态增高，过长退文字。属性条仅表示本卡三项已确认的Lv.1/Rank1/觉醒0次数值比例，无虚构额外加成；上游时间有时区才换算日本时间。未取得的乐队Logo、演出小人等不伪造，SNAP详情独立展示完整横图、多人关联、百分比属性与全部演出/激奏支援技能（EX的两项演出支援均保留）。

成员列表技能数据来自 Haneoka 的日服 API（用户给出的 `/intl/` 是另一数据集，不混用）。`release?projection=identity` 返回版本标识；同一 `release` 下读取 `cards`、`leader-skills`、`skills`、`gekisou-skills`、`skill-reference`，均为完整集合无分页。核对版本 `r-544e9e1285777b600e3f` 的60张卡，ID、assetId、characterId、rarity、cardType、演出与激奏技能ID全部与本地卡库一致。运行时仍逐卡校验身份，冲突显示映射未确认。

技能构成是 leader/live/gekisou 三类。队长摘要展示全属性/技巧值/表现值/表演值、增幅和适用乐队；若有演出技能类别加成，另列其适用成员及加成，不把132%与18%合成无条件150%；演出摘要选择得分增幅和持续时间，并保留LIFE或PERFECT条件；激奏摘要区分JUST/COMBO获得量、叠加上限、LUCK抽选条增量、LUCK点数及概率。不是把所有LUCK解释成同一种加成，也不把PERFECT得分加成称为判定强化。当前日服成员演出均为得分类，无已核实的成员判强/回复样例，不编造这些样例。

统一选 `effects.level=5`，`effectValue` 的百分比除数仅在上游描述明确 `/100` 时使用；数量和pt不除100。条件来自 `skill-reference` 的分组、条件和累计条件。列表摘要保留已核实的描述/效果/条件结构指纹，并允许已知队长属性加成按同版本乐队与目标参数化生成；原始效果、完整日文模板和目标身份必须一致，不因新卡ID或数值变化而要求逐张登记。程序启动读取缓存、主资料同步成功时自动重建摘要，更新失败保留有效旧资料并标旧；未知结构不猜测，不通过模型生成。`700`、起始判定、上限等限定语受结构指纹校验，条件变化必须重新审核。最初60张卡共180份摘要曾与对应版本公开原始数据核对，队长机制指纹同时包含解析后的目标表字段。旧独立缓存缺少队长或同版乐队资料时尝试升级，并保留300秒失败退避；原schema 1可继续读取，升级失败保留已确认摘要。新卡65、66分别显示红色／millsage表现值加成，以及millsage／COMBO激奏成员技巧值加成；两项独立列出，不合并成无条件总值。

沿用现有 asset-cache、素材获取、QQ上传及失败回退，不把大量素材写入源码。公开可访问不等于获得再分发许可，见[第三方说明](../THIRD_PARTY.md)。

## 缓存与代码入口

同步仍获取五份基础列表，随后分别以最多八线程获取成员和SNAP详情并保存索引。普通条件查询只过滤本地数据，不逐卡联网；详情失败保留上次有效内容并标旧。旧缓存启动尝试升级，失败可继续查已有资料；分类索引不完整不能声称给出完整分类结果。首次升级会增加SNAP详情请求，无需新密钥或配置。

Card.catalog / SupportCard.catalog 在磁盘保存于顶层 card_catalog.member/support，原卡牌行结构不变；仍写 schema2 + extended_schema4，旧读者可忽略扩展，card_catalog_version=1 标记新索引。没有清空主缓存、额度或通知记录。

| 文件 | 用途 |
|---|---|
| card_catalog.py | 校验筛选、完整匹配集合、ID/卡面模式、共享结果和文字 |
| yatta.py、data.py | 原始关联、分类、确定性文案、属性状态、兼容缓存和失败保留 |
| commands.py、local_query.py、structured_query.py、query_capabilities.py | 直接命令与本地自然语言共用查询 |
| card_visuals.py、visuals.py、qq.py | 网格、详情、原卡面接入既有回复链路 |
| tests/test_card_catalog.py及现有查询/回复/缓存测试 | 合成样本、真实映射事实、AND/OR、分页、异常、零模型和图像回归 |

QQ人工验收见[LOCAL_QQ_TEST.md](../LOCAL_QQ_TEST.md)。本轮仅在开发工作区验证，不自动提交、合并、部署或发送真实QQ消息。

成员列表另有 `haneoka-member-list-jp.json`，不改变主缓存或详情来源；24小时有效、失败5分钟退避、并发合并、原子替换，失败保留旧缓存并提示；首次不可用则列表仍可显示卡面和ID，技能明确不可用。缓存记录上游release/sourceId和本机获取时间，后者不是上游更新时间。仅在成员列表绘图工作线程访问，不阻塞QQ事件循环，不涉及付费接口。

角色与SNAP详情共用白底信息区、轻阴影和蓝紫标题带，与底纹页面区分。SNAP列表摘要仅接受已核对的Project Yume中文完整效果模板（`support_summary.py`），未知措辞不猜数值，提示按ID看完整效果。列表不再混入属性数值；百分比属性保留在详情。
