# 榜线历史采样与运维

默认 Haneoka 来源使用 `haneoka-cutoff-history-v3.sqlite3`，schema 3；代码读取 tracker／open／haneoka 三来源段，切换处断线，不改写原库。上游参考时钟与接收时间偏差超过60秒时，若同一响应的 HTTP Date 距接收时间不超过5秒，以 `HTTP Date - (serverTimeMs - fetchedAtMs)` 校准历史时间，并在新增的 `clock_calibrations` 表中原子保存原始两项时间和 HTTP 锚点；查询提示秒精度及网络误差。没有可信锚点则记录缺口，同时将分数、原始采集／参考／接收时间、HTTP Date、来源合同及质量状态保存到独立的 `clock_quarantine` 隔离表，不进入曲线或往期有效快照。`clock_pending` 按服／活动／挑战记录持续异常起止时间；同一挑战收到不早于异常末次接收时间的有效观测后解除当前告警，隔离记录继续保留，不自动回填。查询明确提示本次隔离，`/数据状态` 与周期采样状态显示待核验告警，服务器日志记录隔离及恢复，不主动发送 QQ 消息。新表为兼容附表，旧版继续读写原历史；旧版不维护告警状态，新版恢复有效写入时更新。原表及 schema3 不变，支持旧版本继续读写；不回填历史缺口。当前时间与来源合同见 [统一来源说明](HANEOKA_UNIFIED.md)。

可选开放平台适配使用独立 `moenotes-open-history-v2.sqlite3`（可配 `OURNOTES_OPEN_HISTORY_FILE`），旧 tracker v1 保留且不原位迁移。三来源均通过兼容附表保存同次观测的公开玩家ID和用户名，不保存队伍、卡组或完整profile。启用 `open` 前另行完成认证覆盖／时间验收；日额度不形成拒绝或采样降频。配置、schema、回退见 [META_OPEN](META_OPEN.md)。

历史是本机从启用后保存的真实挑战歌曲观测。不补造部署前或停机期间的数据，不是积分档线、永久榜或确认终榜。每次保存前 100 个原始响应位置，只存整数／空值、身份、时间和质量状态，不存玩家、队伍或聊天身份。

## 查询往期活动

`/查榜线 id1`、`/查榜线 活动="名称"`（兼容 `活动名称=…`）读取所选服已保存的活动。可组合 `hk/kr/en`、`歌曲ID=…`、`歌名="…"`、排名或区间及 `仅数值`，参数组顺序不限。`id1` 表示活动 1，大小写不限，也支持 `id 1`、`id=1`、`id:1` 和原来的 `活动ID=1`；裸数字仍是排名。名称完整匹配优先，部分匹配歧义时列活动 ID；没有记录、身份冲突或库不可用时直接提示，不查询当前活动，也不请求上游榜单。

每首歌的分数表选择最近一次有效观测的完整分数向量，并显示该记录的源时间；保留零分、空位与下降，不逐名次取最大值或向较早记录补空位。过期、质量异常、损坏或全空的记录会跳过；同一源时间的来源内／跨来源冲突会排除该时间点，再寻找较早的有效观测，并注明异常时间及原因。原始记录不改写。全部所选排名没有有效分数时返回简短说明，不生成空榜图片。往期图文读取同次有效观测的ID／用户名；旧记录没有身份时说明缺失，不显示整列身份占位，不从其他时刻补人；旧日服记录从目录补齐缺失的活动时间、封面与歌曲封面，不覆盖已保存资料。各曲有效观测时间可能不同，不能据此确认终榜。趋势继续保留来源切换断线与预算限制，超预算不影响有效快照。

后续采样在同一数据库添加 `event_metadata` 表保存活动和歌曲元数据，不含玩家资料，不改变 v1/v2/v3 的版本号或原有表列。旧库没有该表时按 `boards` 中已记录身份查询；日服名称可从内存主资料补充，其他服旧记录缺名称时使用活动 ID。旧版本可以继续读写新增表后的历史库；回退不会删除该表或已有分数。历史查询只读，不创建不存在的数据库。

## 开关与发布配置

榜线图表默认隐藏超过 30,000,000 的历史分数，使用 `OURNOTES_CUTOFF_SCORE_DISPLAY_LIMIT` 调整为其他正整数。等于阈值的分数保留，隐藏点形成缺口，不连接两侧曲线；全部隐藏时显示“无可绘制有效观测”。当前分数表仍显示原值并标注“异常分数”。提示同时进入图片和文字。此阈值只是展示策略，不是游戏理论上限或作弊判定；既有与新采集历史均按查询时配置展示，不改写分数、玩家身份、来源排名或数据库结构。

安装默认历史写入开启、周期采样关闭。Haneoka／open 查询可记录新快照；选用公开 Moenotes（`OURNOTES_CUTOFF_SOURCE=tracker`）时，前台查询仅取最新公开快照，历史只由后台采样写入，默认间隔 300 秒。tracker 不叠加本地榜单成功缓存；同时等待的请求复用刷新，限流退避保留，失败或倒退的源时刻不回退成旧成功榜单。上游仍可能使用自身 CDN 缓存，因此按需查询不等于游戏即时拉榜。原始采集时间超前接收时间超过 1 秒、或服务端参考时间偏差超过 60 秒的采样留为缺口，不用接收时间替换源时间。事件与元数据缓存不变。

只有机器人运行入口启动周期任务，CLI、导入模块和构造仓库不会启动任务。采用 tracker 时必须同时启用周期采样才能积累新曲线；切换来源和启用采样需要部署配置，本地代码更新不会修改服务器配置。发布时将以下配置合入服务器已有配置，不覆盖其他配置或密钥：

可复制的发布预设位于 [query-upgrade-v1.env.example](../deploy/query-upgrade-v1.env.example)；合并 GitHub main 本身不会改写服务器已有环境变量。

```dotenv
OURNOTES_CUTOFF_HISTORY=1
OURNOTES_CUTOFF_SAMPLING=1
OURNOTES_CUTOFF_SAMPLING_SERVERS=jp,hk,kr,en
OURNOTES_CUTOFF_SAMPLING_INTERVAL=300
OURNOTES_CUTOFF_MIN_FREE_MB=512
```

国服 `hk` 转为上游和存储身份 `tw`。采样复用来源限流、合并和退避，按服务器及歌曲逐个处理，前台榜线查询进行时让位并标记缺口。只采 collecting／finalizing 榜；已归档、关闭和未知状态停止抓榜，每 15 分钟以上继续发现下一活动。周期按单调时钟维持 300 秒，不额外累加网络耗时；超时错过的周期跳过，不堆积补采任务。进程结束取消任务，重启继续使用原库。

## 存储与容量

三来源历史分别存储在主缓存旁：Haneoka 使用上述 v3 文件，open 使用 v2 文件，旧 tracker 使用 `moenotes-history-v1.sqlite3`（可用 `OURNOTES_CUTOFF_HISTORY_FILE` 指定）。与当前榜缓存、主资料、额度和通知库独立。所有活动长期保留，没有自动删除任务。代码回退不迁移或删除历史；仅支持旧源的读者继续使用自己的库。

活动结束时间约束游玩期，不是榜单快照的抓取截止时间。来源明确标为 `finalizing` 或 `archived` 时，结束后抓取的同活动／挑战榜单仍可显示并保存，分别标注结算采集中或最后观测（非确认终榜）；活动开始前、其他采集状态下超过结束时间的观测仍拒绝。旧版已标为 `outside_period` 的记录不自动改写；修复后收到的新观测按上述规则判断。

分数用 JSON 整数保存，避免浮点及 SQLite 有符号 64 位分数列的限制。同源时刻同内容去重，新时刻持平仍保留；同一时刻内容冲突保留双方并标为不可绘图。合法晚到点进入历史，不替换较新的当前快照。未知时间、异常时钟、身份冲突和来源错误留下质量或缺口记录。

可用空间低于默认 512 MiB 时暂停新增历史和周期采样，存量不删除，当前榜查询继续工作；恢复空间后下一周期重新检查。`/数据状态` 显示库大小、观测数、覆盖范围、最近成功／失败及采样状态。真实体积取决于活动时间、歌曲数和分数长度，应根据实际积累监测。

绘图只读取一首活动歌曲和所需名次。单次最多读取 20,000 条观测及缺口；超预算时明确退回当前数值，原始记录完整保留。内存不会随全部历史库持续增长，也不长期缓存历史图片。

## 玩家身份与缓存恢复

`observation_players` 是可选附表，以原 `observations.id` 关联最多100个位置的公开ID／用户名；分数、排名位置、源时间、服务器时间与接收时间仍取原观测。附表缺失的旧库可直接读取；版本号1/2/3、原表和原观测不变，旧版本忽略附表且仍能读写分数。重复同次快照可补全缺失字段；已知身份冲突时隐藏该次身份并说明，不选择其中一份，也不影响有效分数。

恢复已有缓存先运行 `python -B scripts/backfill_cutoff_players.py --source tracker --cache-dir <moenotes-cutoff-v1> --history-file <moenotes-history-v1.sqlite3>`。默认只读演练；确认匹配后加 `--apply --backup-dir <新备份目录>`，先执行SQLite在线备份及quick_check，再仅补身份附表。Haneoka使用 `--source haneoka` 及相应缓存／v3库；存在时钟校准时必须通过原来源时间、参考时钟和接收时间精确映射，不能以接近时间匹配。来源、活动、挑战、曲目、源时间和完整分数向量全部对应且无同时间多记录，才允许回填；不按相同分数猜玩家，不新增观测或修改质量。过期快照恢复的身份也只属于该过期快照，不会倒填至较早的有效记录。

## 故障与备份

锁竞争、损坏和写盘失败只影响历史，不使当前查询失败。损坏库不会静默清空或替换。先停止采样并保留原文件，再在副本上排查；勿删除历史、当前缓存或额度文件来修复其他问题。

在线备份使用 SQLite backup API；普通文件备份应先停止机器人并关闭连接。不要在写入中只复制主文件而忽略事务日志。恢复或迁移后先在副本执行 `PRAGMA integrity_check`，核对身份、数量和覆盖范围，再安排服务使用。运行库和日志不进入 Git、wheel 或 sdist。

## 验收边界

`test_cutoff_history.py` 使用合成观测、临时库、假时钟和接口替身验证去重、持平、迟到、冲突、缺口、重启、低空间、锁与损坏。真实四服持续积累、服务器磁盘监控、QQ 手机送达须上线后分别验收；离线测试不证明生产状态。


## 可选历史压缩（不自动迁移）

压缩仅改变物理存储：完整分数载荷精确去重并使用 zlib，同次公开玩家 ID／姓名通过字典保存，查询最近榜单时先筛元数据、再解码选中载荷。来源、原始时间、质量、采样间隔及前台写入策略不变；相同分数但不同有效时间的观测仍分别保留。每个连接最多缓存 256 个载荷及 4096 个字典词，关闭连接后释放，不长期占用读事务。

应用可读取和继续写入压缩 schema 107，也继续支持原 schema 1／2／3。每个压缩库保存原 schema，防止 tracker／open／haneoka 的库串用。schema 106 属于旧实验格式，本入口不直接接收。新建库仍使用原格式；升级代码不会压缩或替换现有正式库。

在 checkout 使用离线副本操作（路径只是示例）：

```powershell
python -B scripts/compress_cutoff_history.py compress backup.sqlite3 compressed.sqlite3
python -B scripts/compress_cutoff_history.py check compressed.sqlite3
python -B scripts/compress_cutoff_history.py export compressed.sqlite3 restored.sqlite3
```

`compress` 要求输入为已关闭并完成 checkpoint 的一致性备份，拒绝非空 WAL／journal；不能将运行中主库直接复制后当作完整备份。输出必须是独立新路径。工具不读取生产配置、不停止服务、不替换运行路径。每批 256 行与迁移进度同事务提交，失败保留 `.partial`；用完全相同的源和目标重跑可续迁。源文件摘要变化拒绝续迁。SQLite 完整性、引用校验和所有原业务表逻辑摘要一致后才发布新文件，不覆盖既有目标。初始化阶段尚未形成完整元数据的 partial 不可续迁，保留错误文件并改用新目标重做。

压缩后的继续采样使用同一事务保存载荷、字典、观测及附表；获取成功和历史写入失败仍分别处理。损坏检测校验压缩帧、载荷摘要和字典词摘要，`check` 报告载荷／字典 ID 与原因，不输出玩家值，不重建空库。共享字典损坏可能影响多条观测，应从可靠备份恢复。

回退旧代码前，须先对包含所有最新写入的压缩库执行 `export`，生成并验证原 schema 的完整新副本，再按受管停写／切换流程替换路径。导出在单个只读快照内，不能包含导出快照之后的新增写入；正式切换必须停写或单独解决增量追赶。旧代码会拒绝 schema 107，不能只回退代码而继续使用压缩库。导出也保留后来新增的时钟隔离／校准表与业务索引，失败保留 partial；导出失败后使用新目标重试，不覆盖旧结果。

本机旧备份 129.88 MiB 压缩后主库 20.19 MiB（约减少 84.5%）；这是旧样本的测量，不含运行 WAL、备份或迁移临时空间，不保证所有活动相同比例。新库不改变数据保留时长，也不删除时钟异常记录。部署及正式库迁移需分别验收，此工具没有自动上线动作。
