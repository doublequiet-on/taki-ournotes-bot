## 图片故障：证据、修复与限制

本机运行日志在 2026-09-28 出现以下三类失败（时间为本机日志时间）：

| 查询 | 编码体积 | 失败证据 |
|---|---:|---|
| 分数表 | 3,647,549 B | 02:50:52 查询完成，02:50:58 SDK 请求超时 |
| 角色详情 ID 53 | 1,745,171 B | 13:38:59 查询完成，13:39:04 SDK 请求超时 |
| 谱面 | 2,179,603 B | 13:45:28 查询完成，13:45:33 SDK 请求超时 |

这些样例支持“约5秒上传超时”，不支持将所有失败归为 QQ 文件硬上限。已安装的 `qq-botpy==1.2.1` 源码确认默认 HTTP timeout=5，`BotHttp.request` 超时后返回 None，调用方因此记录缺少上传回执。

- 所有渲染器经 `visuals._bytes` → `image_output.encode_image` 共用预算：JPEG≤1,500,000 B（base64≤2 MB，不含少量 JSON 开销），最长边≤8192，像素总量≤1200万。这是本项目保守预算，不是官方硬限制。
- 保留整图；优先调编码质量，再等比缩放，不裁图、不删列表行、不额外拆成多条群消息。复杂长图清晰度存在体积取舍，可按页或 ID 看详情。
- `_upload_image` 只为上传使用30秒 timeout；使用 SDK HTTP 的临时副本共享已初始化会话，不修改并发消息请求的默认值。副本在 finally 中解除会话引用，防止 SDK 析构函数误关闭原会话。
- 上传入口再次检查大小，防止未来新增输出绕过编码预算。失败仍回退同份文字；媒体消息发送结果不确定时不自动重发。`srv_send_msg=False` 和现有顺序、被动回复序号保持不变。
- 没有使用真实 QQ 验证这次修复，不能承诺消除网络抖动、平台审查或其他服务端拒绝。

离线真实卡面预览复测（仅本地文件）：角色列表约4.58 MB→1.42 MB，角色详情2.61 MB→1.32 MB，SNAP列表3.11 MB→1.37 MB，SNAP详情1.85 MB→1.27 MB。保留同样内容；不同图片编码体积会变化。

## 模块职责与后续维护

| 入口 | 唯一职责 / 约束 |
|---|---|
| `card_catalog.py` | 条件解析、选择、去重、分页和列表/详情/卡面模式；不依赖 QQ SDK |
| `yatta.py` / `data.py` | Project Yume 原始字段、分类证据、详情和兼容缓存 |
| `haneoka_members.py` / `haneoka_member_contracts.py` | Haneoka 日服成员列表数值、条件、实体映射和已核实机制指纹；未知机制拒绝猜测 |
| `card_visuals.py` | 两类卡与输出模式分流、通用文字/图像放置 |
| `member_list_visuals.py` | 角色网格、条件标签、按截图绘制的边框 |
| `member_detail_visuals.py` | 角色详情与两类详情共用的区块绘制 |
| `support_summary.py` / `support_visuals.py` | SNAP已核实模板的基础效果摘要、独立列表/详情 |
| `image_output.py` | 平台无关的统一编码预算；不得在每个命令重复压缩逻辑 |
| `qq.py` | 上传 timeout、结果发送、顺序和回退；不得把消息身份放进业务层 |
| `update_notice.py` | 保留已上线的一两句群友可见公告、防重复和回执状态；不建立第二套发布通知 |

新增技能机制必须先核实上游效果、触发条件、单位，再扩充指纹/模板和离线样例。不要从技能名称随意提取一个百分比当作完整效果。列表摘要与详情的数据来源不同，图片明确标注，不能互相冒充。
