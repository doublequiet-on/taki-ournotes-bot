# Haneoka 默认资料入口

当前提供主资料、完整谱面、活动与榜线；歌曲分数表及三个专用来源已移除。旧分数表缓存留存但不再读取或刷新。

## 默认配置与请求范围

| 配置 | 默认 | 数据与限制 |
|---|---|---|
| `OURNOTES_DATA_SOURCE` | `haneoka` | JP 歌曲、角色卡、留影卡、人物、卡池、静态活动、属性、技能及原生属性图标；中文仅合并通过身份与规则核对的 intl 文本 |
| `OURNOTES_CHART_SOURCE` | `haneoka` | 固定 JP release 的完整谱面；失效仅用本来源已验证缓存 |
| `OURNOTES_CUTOFF_SOURCE` | `haneoka` | 四服 Game Records 活动与 Top 100 观测，上游为 MoeNotes tracker |
| `OURNOTES_CACHE_TTL_HOURS` | `0.5` | 主资料缓存有效期；QQ 后台对齐香港时间每个整点与半点刷新 |

实际应用入口 `Settings.from_env()` 使用上述默认；已有环境变量优先，因此升级代码不会覆盖明确写着旧源的生产配置。内部 `SongRepository` 和直接构造 `Settings` 的历史默认保留兼容，运行入口始终显式传入配置。不读取或覆盖旧源缓存、历史与额度。

主资料启动时加载，后台完成一次刷新后重算下一整点／半点，错过时段不补跑。

默认主资料、谱面、榜线和各自素材的应用网络出口为 Haneoka。图标缺失退回现有文字／颜色展示，不从旧源补图。历史读取保留本地旧源库，来源切换断线；这不产生旧源联网请求。显式旧源配置仍可联网到旧提供方。

成员摘要在启动解析原始缓存和每次资料同步时重建，与卡牌一同发布。常见队长属性加成除原精确指纹外，支持经过完整日文模板、Lv.5原始效果和同版本乐队／目标核对的参数化规则；新ID、数值和已知目标组合不再需要逐卡登记。仍拒绝额外条件、混合属性、缺失效果和未识别目标，不自动批准新机制。默认主资料已有所需字段，不增加下载；显式旧主资料的摘要源增加一次同release的bands请求，旧schema 1无该字段仍可读，并在有网络时升级。

## 活动与榜线

新增 `/查活动 [jp/hk/kr/en]`，复用所选榜线来源的当前／最近活动，提供名称、状态、时间和挑战歌曲 ID，无玩家排行请求。时间按各服时区显示。

`/查活动 列表／历史／ID／名称` 使用主快照已收录的日服静态活动；奖励卡、指定加成卡和展示卡分开关联，不由静态歌曲关联推断挑战歌曲，也不附当前榜线指令。当前日服活动补充静态卡牌关系前，必须同时匹配活动 ID 与起止时间。

`/查卡池` 与 `/查角色` 也读取同次捕获的主快照：卡池按日服起止时间查询当前／历史并区分 UP 成员卡、留影卡；角色按独立人物目录查询姓名、昵称、ID或乐队，不依赖已有关联卡。零时间表示未确认，起止均已知却倒置或相等时拒绝该快照；卡池时间窗不证明个人可抽资格。旧缓存未含对应集合时报告资料未获取，不把缺失解释为空集合。新增领域记录与歌曲、卡牌在同一发布锁内更新，不增加独立刷新任务或修改缓存 schema。

`event_metadata.py` 使用 Haneoka event-tracker 的首选静态区域：日服→jp，其余→intl，不跨静态区回退。活动 ID 和开始／结束时间必须与实时 DTO 一致；挑战 ID 与 songHref 的 musicId 必须匹配，才附加名称和固定版本素材。失败时保留实时 ID 与时间；未知名称不从其他源补全。每 300 秒检查 release，失败至少 60 秒后重试，旧静态资料最多使用 24 小时。

Game Records 过滤过非法挑战条目，仍无法证明原始序号完整，因此拒绝“歌曲1／歌曲一”；请用歌名或 `歌曲ID=100111`。排名保留响应位置与空槽，不按分数重新排序。按用户确认，单纯的上游／本机时钟偏差不阻止显示，也不添加偏差提示；新鲜度按上游参考时钟与采集时间之差，加本地经过时间判断。两项时间保留原值，不改用本机获取时间。缺失时间、采集时间明显晚于上游参考时钟、期外和过期快照仍拒绝，安全整数及活动身份校验不变。

上游参考时钟与接收时间相差超过 60 秒时，Haneoka 历史库只记本地采样缺口，不保存该分数／源时间点；查询、后台采样、缓存回退和迟到响应使用同一规则。时钟恢复后继续保存，并在缺口处断线。当前分数照常可查。

## 兼容与已知限制

- 活动静态缓存为 `haneoka-event-metadata-v1/`；与主资料和榜线缓存分离。
- 原主资料缓存增加可选 ui-marks 资源，领域属性图标字段有缺省值；旧转换器忽略新增资源，原文件 schema 不变。历史 Haneoka schema 3 保留。
- 上游得意乐曲 tag 的正式名称关联仍未确认；不猜 tag ID 等同乐队 ID，相关查询明确不完整。
- 实源 JP release `r-073d884b07d594061fd6` 的成员卡 64 激奏 Lv.5 缺第二项效果，继续标记参数未确认，不拿 Lv.4 代填。
- 2026-10-09 08:06–08:10 UTC 本地实源核对：87 首歌曲、67 张角色卡、68 张 SNAP，四服活动 2 的名称及挑战链接通过日期身份校验，日服活动横幅和三曲封面成功下载。
- 2026-10-09 实源发现 DTO 上游时钟比本机／HTTP Date 快约两分钟；按用户确认规则复核四服共 12 个挑战榜，各有完整 100 行分数，均正常显示且无偏差提示，历史只有 12 个采样缺口、0 个偏差时间点。实源、CI 与生产发布分别验收。

## 验证入口

`test_haneoka_event_metadata.py`：四服静态映射、时间／歌曲错配、损坏缓存、无排行的活动查询、素材 release；`test_source_egress.py`：实际下载调用链的主资料／谱面／卡牌和歌曲渲染／四服采样出口，离线网络桩不证明上游可用。

实源预览与探测写入工作区忽略目录 `runtime/haneoka-unification/`，不覆盖生产。完整回归、包内容检查、发布 CI、服务启动与 QQ 实收分别验收。上游合同见 [固定版本说明](https://docs.haneoka.org/concepts/servers-and-releases/)、[歌曲分析页面](https://haneoka.org/jp/zh-CN/song-meta/)。
