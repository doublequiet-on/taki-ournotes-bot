# 单图优先与统一美工

QQ 图片回复使用已确认的 Haneoka 风格：浅底、Noto Sans SC／Roboto、原尺寸字号、紧凑分组和游戏图标。原卡面与固定彩蛋保留原输出。`/查留影卡` 为正式名称；旧 `/查支援卡`、英文／日文别名继续兼容。@ 回复行为不变。

## 完整性与发送规则

1. 列表绘制捕获的完整结果，不再按 16 条截取。有效的旧页码语法兼容为完整列表；越界页码仍提示错误。文字 CLI 保持原分页接口。
2. 先测量实际文字、行高与完整内容，再决定画布和分栏。正文不为凑单图而缩小。角色卡保留队／演／激；未知技能显示完整已知说明。
3. 颜色按红、蓝、绿、黄、紫纵向；每种颜色内 SSR、BD／EX、SR、R 紧凑排列，不预留空稀有度列。成员顺序来自 Haneoka。技能起始位置在本排对齐。
4. 目前项目保守编码预算为 12,000,000 像素、单边 8,192 像素、1,500,000 字节（并非 QQ 官方上限）。超过预算只拆完整卡片行／详情区块／排名行／谱面列，保留原字号。单个不可分单元也超限时退完整文字，不裁剪内容。
5. 单次被动回复容量不足时发送可容纳部分，剩余编码结果保存在当前会话，提示 `/继续`。续发不重新筛选或重新生成；编号连续，`/选 N` 只允许已确认交付的条目。
6. 图片上传失败，短文字直接回退；长文字分段保留并提示 `/继续`。发送回执不确定时不自动重发，也阻止不确定批次自动续发。
7. 续发沿用上下文时效、容量和身份隔离；重启、新查询或上下文过期后需重新查询。待发图片累计超过 128 MB 时优先淘汰旧上下文；最新单份捕获结果不会因该软上限而丢尾部。不会降低图中文字尺寸换取留存。
8. 未获取的数值、身份、图像、技能和历史明确保留未知状态。历史断点不连线；榜线不推算未来或假定终榜。

## 模块与素材

- QQ `_render_prepared` 向新 `*_layout.py` 传入同次查询数据及素材回调。`readable_pages.render_parts` 负责完整分段，`encode_image(preserve_size=True)` 禁止降尺寸。
- `visual_skill_contracts.json` 保存人工确认摘要与机制／日文模板指纹，匹配失败退完整技能；条件增强与等级成长分别展示。
- 等级按对应服务器成长曲线和觉醒上限计算，缺资料不猜；玩家头像、角色卡和留影卡使用属性、等级、觉醒角标与稀有度渐变框。渐变框为本项目绘制，稀有度与觉醒图标为游戏原图。
- 字体按 OFL 随包分发。游戏图标与 note atlas 不打包；`game_assets.json` 固定来源和 SHA-256，运行时按需匿名加载到 `runtime_data_dir()/game-assets`。失败暂缓 60 秒再试，角标退文字；原版 note 不可用时完整谱面退资料文字。其他卡图继续既有受限素材缓存。
- 字体、测量和 note 重建使用有界缓存；解码缩略图 LRU 上限 32 MB，调用者拿独立副本。列表素材并发最多 3。

相关测试：`test_single_image_upgrade.py`、`test_readable_pages.py`、`test_visual_upgrade_contracts.py`、续查／消息顺序／数据来源与安装检查。离线画廊覆盖 105 个模板和状态，网络关闭；原 note 验证可传 `--game-assets-dir` 指向已有哈希素材缓存。
